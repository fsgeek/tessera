**C8. Do all required signers attest to the same content — and in
what frame structure?** (S-P2, review item 12.) Two honest signers
under one manifest can sign *different* payloads and the verifier
accepts; P2's text never says "common content"; the frozen plan
assumed it. **Correction (2026-09-11, Codex pre-read; verified against
`sp2_q2_degraded_compromised.pv` lines 188 and 190):** this file's
first recommendation — "one framed byte string, equality across slots"
— would *break* legitimate two-key acceptance, because each signer's
frame carries that signer's own fingerprint (`=fp(kA)`, `=fp(kB)`) and
under perfect fingerprints two such frames can never be equal. The
question therefore has a framing fork the earlier text hid:
- **(a) Common attested content in separate, signer-specific frames.**
  The six non-fingerprint fields (object type, algorithm, identity,
  manifest hash, canonicalization version, payload) must be equal
  across slots; only the key-fingerprint field differs. P3's field
  list (fingerprint inside the signed bytes) is preserved per signer.
  Three of the six are already enforced through the shared manifest
  tuple (`=alg`, `=id`, `= h(t)` in each slot); the verifier gains the
  other three — object type, canonicalization version, payload — and
  a splicing companion goes red (count corrected 2026-09-11, Codex
  second pass).
- **(b) One shared frame** whose key binding lives in the manifest
  (the manifest hash pins the signer set, S-P3 F3) rather than in a
  per-signer fingerprint field. One byte string, one equality — but it
  changes P3's registered field list for multi-signer objects and
  P8's frame layout.
*Recommendation:* **(a).** It states what "the canonical signed bytes
commit to the required-signer manifest" plainly meant, changes no
registered field list, and costs three new equalities (object type,
canonicalization version, payload — the other three are already
carried by the shared tuple) and one companion.
*On (b):* an amendment to P3's field list and P8's frame precedes any
model. *On neither:* a multi-signer attestation is a set of per-signer
attestations of possibly different bytes, and the relying-party story
says so.
