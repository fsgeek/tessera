# Amendment 12 r3 — findings (2026-11-20)

Scope: A12.1–A12.2; sections 3–5 excluded. The two choices in `docs/reviews/amendment-12/DISPOSITION.md:28-37` are resolved and are not reopened. HIGHs are classified against the round-3 exit. The draft and its prospective duties are not evidence of deployed behavior.

## A12-R3-01 — HIGH / PROMISE: a pre-deadline start need not result in COMPLETE, and the deadline read does not establish the stated tie

`docs/phase-0-prereg-amendment-12.md:40-41,48-53,65-67` says a completion begun before L_term ends COMPLETE and proposes a clock read followed by a separate commit. Suppose the read is just before L_term, then the invocation dies before its conditional write, or a later invocation fences its delayed write. No COMPLETE was recorded; at the next visit the deadline rule refuses it. This can occur with the stated dependencies available. Conversely, reading at L_term minus one millisecond and being descheduled until after L_term before initiating the write violates the stated cut if “begun” means initiating the write. The DynamoDB condition compares version and lifecycle, not time (`service/issuer/tessera_issue/aws.py:88-104`). A wall-clock step backwards can also give a later invocation a pre-deadline reading after an earlier invocation observed the deadline (`service/issuer/tessera_issue/service.py:42,49-50`); bounded skew is not monotonicity. Define the decision event in terms of the reading and durable fencing, including crash, supersession and uncertainty, and condition or narrow the claim that a pre-deadline start wins. This is a promise finding even though the implementation and model are future duties. A material change to the adopted latch override or its consequences belongs to the author; do not treat a steward's new tie as the author's ruling.

## A12-R3-02 — HIGH / PROMISE: detection and eventual cleanup are asserted as current guarantees without their prerequisites

`docs/phase-0-prereg-amendment-12.md:57-58,73-75` says D10 alarms on any request open past L_term + 1 hour and that cleanup succeeds eventually. D10 is a detection contract with tests and deployment still to be built; its current row says open over 24 hours until L_term is live, and gives an alarm latency rather than establishing a deployed L_term monitor (`docs/V1-DETECTION-CONTRACT.md:4-5,22,65,72`; `service/issuer/DEPLOY.md:94,107-113`). A stalled request can therefore remain open without that alarm. Cleanup can also continue to fail indefinitely: the code catches errors and retains the obligation (`service/issuer/tessera_issue/pipeline.py:276-279,308-335`). A result object written before a failed COMPLETE can remain in S3 after REFUSED; the normal receipt API does not mint a URL for a refused request, but an S3-authorized principal can retrieve the remaining object. State detection and cleanup as duties conditional on deployment, functioning monitoring and eventual successful retries, without claiming capture visibility.

## A12-R3-03 — HIGH / DUTY: terminal progress and the access boundary need complete conditions and a testable fence

`docs/phase-0-prereg-amendment-12.md:52-56,59-75` makes refusal conditional on a visit and successful writes, but does not specify a durable outcome for an ambiguous or indefinitely pending COMPLETE write, or eventual repeated visits and successful operations. For example, after a pre-deadline clock read the terminal write is delayed; the next invocation must fence it before refusing, and if fencing or a required read never completes neither terminal state is recorded even when scheduling, S3 configuration and the listed store services are nominally available. The code's CAS and `_fence` do fence an older *record write after the new bump*, not an S3 put (`service/issuer/tessera_issue/pipeline.py:245-261,1222-1228`). API upload completion is another version-CAS writer (`service/issuer/tessera_issue/api.py:98-106`); the poller has reserved concurrency one (`service/issuer/infra/main.tf:358-365`). The content-addressed key and COMPLETE-only URL are prospective; current API URLs name the fixed key (`api.py:165-185`). Define ordering and retry/fairness and ambiguous-write handling, the principals included in “client path,” and test a stale put plus fetch. A hash-derived name also needs enforcement that the bytes written match the name and cannot be replaced with different bytes. The normal current API path found does not deliver a receipt for a request durably REFUSED, but a stale fixed-key put can overwrite the object fetched for a different winning COMPLETE record, as r2 described. These duties are gates before enabling the bound, not present proof.

## A12-R3-04 — HIGH / PROMISE: the minimum gap is not established by the stated fence

`docs/phase-0-prereg-amendment-12.md:122-135` promises at least nine days without acceptance, but the listed successor fence does not require successor not-before to have arrived. Example: last old request ends immediately after an acceptance 216 h before old not-after; publish, validate and deploy a successor with not-before one second after old not-after while still nine days early. All item 5 conditions can be satisfied early. The current API separately checks its configured not-before (`service/issuer/tessera_issue/api.py:127-134`), but item 5 does not make that check a successor-fence duty or account for old in-flight API invocations. Require successor acceptance to respect its not-before, and fence/drain old API invocations and acceptance writes before treating the old request set as closed. Otherwise an old invocation can accept after the steward observes a drained set and replaces DNS, recreating the old-snapshot stranding that drain was meant to remove. A new Lambda version alone (`A12:123-125`) does not specify routing, in-flight invocations, or an atomic acceptance stop. The accepted gap is not an open choice; the promised mechanism needs to establish it.

## A12-R3-05 — MEDIUM: gap duration and dates assume a bound the draft explicitly does not promise

`docs/phase-0-prereg-amendment-12.md:130-133,160-165` says drain takes “up to 14 days after the last old acceptance” and about February 6 if termination assumptions hold. The cap is the deadline for starting a decision, not a terminal-time bound: even with available dependencies a visit may be deferred and a pre-deadline write delayed (`A12:50-57`). For a January 23 acceptance, L_term is February 6, but termination and drain may be later without any assumption failing. Likewise an earlier acceptance stop does not necessarily move successor opening or every other date earlier: publication, propagation, deployment, not-before and actual final acceptance may differ. The January 23 and 28 latest L1 stops and January 9 notice date are correctly calculated from the February 1 endpoint (`service/issuer/config/window.json:17`; `docs/V1-SERVICE-RESOLUTIONS.md:42`). State February 6 as the latest-acceptance request's deadline, not drain completion, and leave the actual opening conditional.

A9's original one-window record is also summarized in `formal/p8/ENCODING-V1.md:46` and `formal/p8/PROOF.md:55,507`; distinguish historical descriptions from operative global assertions and locate their frozen counterparts. A successor makes a global single-window statement false; quote and qualify the affected operative sentences rather than claiming an exhaustive inventory. A10.4.1 is conditional on the listing option: check the adopted listing CUT and do not silently reactivate its successor-release gate. The existing freeze bytes remain unchanged.

## A12-R3-07 — LOW: vector construction and existing snapshot residual need more precision

`docs/phase-0-prereg-amendment-12.md:119-121,139-149` correctly identifies the two C4 inequalities and separate channel and height checks (`service/verifier/tessera_verify/verify.py:283-289`), but the single-mutation instruction cannot literally cover the two positive vectors and changing a signed declared time requires corresponding valid signatures and anchors. Define the logical mutation and regenerate dependent evidence while keeping unrelated predicates passing. The old DNS snapshot substitution also needs a valid time-compatible snapshot; otherwise `SNAPSHOT_TIME` precedes the claimed channel reasons (`verify.py:256-257,285-289`). The present `SNAPSHOT_IMPOSSIBLE` path applies only when its evidence predicate establishes impossibility, not to every attempt that cannot obtain a snapshot (`service/issuer/tessera_issue/pipeline.py:1185-1195,1205-1215`). An unavailable resolver can instead leave the request open. The drain removes r1's specific early replacement race only if the old acceptance fence is effective (R3-04); the bounded snapshot residual remains.
