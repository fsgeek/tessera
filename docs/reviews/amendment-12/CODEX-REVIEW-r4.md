# Amendment 12 r4 — scoped findings (2026-11-20)

## A12-R4-01 — HIGH / PROMISE: the absolute deadline statements contradict the per-invocation rule

`docs/phase-0-prereg-amendment-12.md:40-41,56,183-184` says that from L_term the only permitted ending is refusal, that the issuer stops trying to complete, and that from February 6 it only refuses the example request. Yet `:48-51` expressly permits a later invocation to read before L_term after an earlier invocation read at or after it. If the first refusal does not become durable, the later invocation may try and durably commit COMPLETE under that rule. Even without a backward clock step, a pre-deadline completion write can commit after L_term before a later fence wins; the version guard does not compare time (`service/issuer/tessera_issue/aws.py:88-104`; `pipeline.py:245-261`). Thus R3-01's pre-deadline success promise is removed, but the replacement retains an incompatible absolute promise. The surviving rule can be stated in terms of each invocation's reading and the durable winner, without promising a real-time cutoff.

## A12-R4-02 — HIGH / PROMISE: dates alone do not establish a nine-day real-time gap

`docs/phase-0-prereg-amendment-12.md:138-140,147-150` treats the successor's not-before check on the issuer clock as proving that no acceptance occurs before the UTC date. The API reads its clock before the separate acceptance write (`service/issuer/tessera_issue/api.py:127-143`), and r4 assumes bounded skew rather than exact UTC (`A12:48-51`). For example, if the old clock is behind UTC and the successor clock ahead, an old acceptance can be recorded after the old cutoff in real time and a successor accepted before its not-before in real time; with a successor not-before only one second after old not-after, the actual gap can be less than nine days. An old invocation can also delay its create after its clock read. Waiting for the maximum invocation time before declaring the old set closed (`A12:136-137`) addresses the drain race but does not undo that acceptance or establish the claimed duration. The date arithmetic holds for the clock readings, subject to L1, not for actual acceptance events without additional clock and commit-time margins. R3-04's missing not-before condition is addressed, but its minimum-gap promise remains unconditioned.

## A12-R4-03 — HIGH / DUTY: the fence and object boundary still require implementation conditions

`docs/phase-0-prereg-amendment-12.md:71-76` describes the existing fence as the refusal sequence and says an abandoned object is unreachable by any client credential. The fence only rejects an older record write **after** its own guarded bump succeeds (`service/issuer/tessera_issue/pipeline.py:255-261`); a pending earlier write can win first, requiring a reread and a decision based on the durable state. It does not fence S3 puts. The current API mints URLs for a fixed object key (`service/issuer/tessera_issue/api.py:165-185`), while the poller has put access to that namespace (`service/issuer/infra/main.tf:239-242`). The proposed hash-key boundary must enforce that each put's bytes hash to its name and that a stale put cannot replace the winning object with different bytes; a name alone does not enforce either. Test a delayed put and fetch, and define the handling of a fence that loses to an ambiguous prior write. These remain prospective gates, not evidence that the current deployment satisfies the stated safety property (R3-03).
