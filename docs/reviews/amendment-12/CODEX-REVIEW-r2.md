# Amendment 12 r2 — findings (2026-11-20)

Scope: A12.1–A12.2, read-only review of the draft, registered sources and issuer/verifier code. Sections 3–5 were excluded. HIGH findings remain; the pre-registered exit therefore calls for another full round. The two choices in `DISPOSITION.md:28-37` are resolved, not re-raised. The draft remains unsigned; its future model and code work are not evidence of a deployed guarantee.

## A12-R2-01 — HIGH: the deadline test cannot establish the stated commit-time tie

`docs/phase-0-prereg-amendment-12.md:39-42,54-56` says a request not COMPLETE at L_term is refused and a COMPLETE commit happens strictly before it. A clock read immediately before a remote DynamoDB write cannot establish when that write commits. For example, the poller reads L_term − 1 ms, sends its conditional put, and DynamoDB commits at L_term + 1 s: the version/lifecycle comparison (`service/issuer/tessera_issue/aws.py:88-104`) contains no server-side time condition. Conversely a delayed write can remain pending across another invocation until a new fence actually commits. A wall-clock adjustment can also move the issuer reading backward; no bounded skew or monotonic wall-clock assumption is stated. Define an implementable linearization rule and its clock/failure assumptions, and reconcile it with the exact deadline promise. Changing the promise about a completion crossing the deadline is a material author decision if outside the adopted choice.

The existing code does not yet implement this tie: `_ship` stores the object and calls `_end_request` with no L_term check (`service/issuer/tessera_issue/pipeline.py:1222-1228`); `_end_request` reads time before the conditional write (`:264-275`). The future model must represent the read/write interval, rather than make them one instantaneous action by assumption.

## A12-R2-02 — HIGH: eventual poller and request-store availability do not imply either terminal state or a one-poll bound

`docs/phase-0-prereg-amendment-12.md:61-66,83-85,103-105` guarantees refusal at the first available poll and termination within ten minutes. A scheduled invocation is not a guarantee that the particular request is visited: the bounded, paginated poller defers work when its budget is exhausted and the index is eventually consistent (`service/issuer/tessera_issue/pipeline.py:168-225`). A large backlog or index delay can extend beyond one interval even with a continuously healthy poller and writable request store. Further, the existing terminal write first requires `cleanup_put` and the poller's `from_env` first reads `config/window.json` from S3 (`pipeline.py:264-267`; `service/issuer/tessera_issue/lambda_app.py:41-44,61-65`). If S3 remains down and the poller cold-starts, the poller cannot reach the request store at all although the scheduler runs and DynamoDB accepts writes; neither COMPLETE nor REFUSED can be recorded. Even a running process can fail the prerequisite cleanup write, or fail its request read/index/cursor operation. Specify the required dependencies, fairness and bounded service/queue delay, or weaken the real-time guarantee. Eventual availability alone cannot imply L_term + 10 minutes, and the drain and dates must inherit the corrected assumption.

The current code explicitly refuses to end a latched attempt (`pipeline.py:269-271`); A12 requires a future change, not a present deadline implementation. API upload completion also writes a request record with version CAS but no lifecycle guard (`service/issuer/tessera_issue/api.py:98-106`; `aws.py:88-96`), so “only the poller writes lifecycle state” and “every write” has both guards (`A12:50-53`) overstate the cited implementation. The API also creates ACCEPTED or REFUSED records (`api.py:127-145`). State precisely which transitions are single-writer and which writes are fenced.

## A12-R2-03 — HIGH: COMPLETE-only URL issuance does not fence the object subsequently fetched

`docs/phase-0-prereg-amendment-12.md:57-60,76-79` asserts that a stored object whose COMPLETE did not land is never served. The API mints a five-minute S3 URL to the mutable key `result/<rid>/receipt.json` after observing COMPLETE (`service/issuer/tessera_issue/api.py:22,165-185`; `aws.py:294-296`); `_ship` writes that same key before its guarded lifecycle commit (`pipeline.py:1222-1228`). S3 bucket versioning is disabled (`service/issuer/infra/main.tf:89-93`). If an earlier stale worker's put is delayed, a later worker stores receipt A and commits COMPLETE, the client receives a URL, then the earlier put overwrites the key with receipt B and its CAS fails, the URL serves B. The database CAS fences the record, not the object. The returned digest is for A and can reveal the mismatch to a client that checks it; it does not prevent delivery of B. A pre-signed URL is direct S3 delivery, not delivery by the API itself.

For a request whose only terminal state is REFUSED, the normal API path does not mint a URL: status requires COMPLETE, and terminal CAS protects against a competing durable COMPLETE. I did not find an ordinary client path that obtains a prior URL for that same refused request. Nevertheless the failed worker's object can remain in S3 until cleanup succeeds, including after REFUSED: cleanup is asynchronous and can fail (`pipeline.py:276-279,308-335`). A stale put can also arrive after the first deletion; the lease/retry is an eventual cleanup mechanism, not immediate non-retrievability to an S3-authorized principal. The requested assurance needs an immutable/content-addressed or otherwise fenced object and an explicit access boundary, plus a model/negative control that covers object overwrite and URL fetch, not only durable state.

## A12-R2-04 — HIGH: drain preserves the old TXT value but does not ensure a usable snapshot, and replacement can strand successor work

`docs/phase-0-prereg-amendment-12.md:102-106` removes r1's specific premature-replacement race for old requests, provided the drain is complete and no other actor replaces the record. It does not ensure the old attempt can capture a *usable* snapshot: snapshot selected T and confirmation must fall in the declared-time interval (`service/verifier/tessera_verify/verify.py:256-257`); an old attempt waiting beyond that interval cannot make a new valid snapshot merely because the old TXT remains. For example, a snapshot needs recapture after its allowed confirmation window has passed; it can be discarded as `SNAPSHOT_IMPOSSIBLE` (`service/issuer/tessera_issue/pipeline.py:1205-1215`). This residual is distinct from the adopted 14-day cutoff and must be stated rather than claiming snapshot ability until the attempt ends.

The reverse cutover is also unspecified. Immediately after the authoritative TXT replacement, a recursive resolver can still return the cached old value; the issuer uses `DNS_RESOLVER` (default 1.1.1.1), checks the captured value against its configured assertion, and retries when they differ (`service/issuer/tessera_issue/lambda_app.py:55`; `pipeline.py:739-748`). If successor acceptance starts at publication, a successor request can lose its snapshot opportunity while old cached DNS persists, eventually being refused. A drain, propagation/validated snapshot readiness and an acceptance fence are needed; the current issuer caches its window configuration in a warm Lambda (`lambda_app.py:43,61-65`), so changing the S3 file alone does not establish a coordinated cutover. Define the actual cutover and disclose remaining bounded-snapshot loss; whether to accept any newly introduced irreversible loss is an author decision, not an invitation to revisit the already adopted gap or latch choices.

## A12-R2-05 — MEDIUM: the change inventory leaves registered sentences in conflict

The A2.1 sentence immediately after the quoted boundary tie says expiry and final refusal apply “only strictly after the boundary, and only to attempts with no timely-latched eligibility” (`docs/phase-0-prereg-amendment-2.md:157-160`). A12 can refuse a timely-latched final attempt at L_term even before or after that per-attempt boundary, yet `docs/phase-0-prereg-amendment-12.md:15-22` does not quote this separate restriction. A request accepted long before its last attempt was allocated can reach L_term while that last attempt is timely latched: both rules cannot hold as written. Quote and locate the affected sentence and qualify it for the adopted deadline.

The successor inventory quotes A9 and labels the frozen profile sentence descriptive (`A12:90-93`), but does not quote the registered `formal/p8/ENCODING-V1.md:711-715` statement “For V1 there is one window … with no overlapping successor”, or the corresponding frozen copy (`formal/freeze-v1/objects/spec.bin:4091-4093`). A successor makes “one window” false as a global statement, although one window per record and the byte/check rules remain intact. Register the textual qualification with its locators, including the actual profile sentence at `docs/V1-PROFILE.md:725-726`, rather than presenting it as unchanged. Also distinguish the profile's path requirement (`V1-PROFILE.md:778-780`) from the per-record checks; the selected same path does supply the new rotation path.

## A12-R2-06 — MEDIUM: gap and first-window dates are conditional, and the client communication ruling is incomplete

`docs/phase-0-prereg-amendment-12.md:110-115,136-140` correctly derives a minimum nine-day gap from L1's 216 h stop and inclusive strictly ordered endpoints, and approximately fourteen days if the last request is accepted at the stop and runs the full bound. With the actual endpoint `2027-02-01T00:00:00Z` (`service/issuer/config/window.json:17`), the latest L1 stops are Jan 23 00:00 UTC and Jan 28 00:00 UTC. But L1 allows an *earlier* acceptance stop (`docs/V1-SERVICE-RESOLUTIONS.md:42`): if it is Jan 20 and the last request runs 14 days, the no-acceptance period to drain is about 14 days from Jan 20, not necessarily 14 days from the announced stop if the final acceptance was earlier still. Publication and successor opening can also be later than drain, and the asserted Feb 6 latest old end depends on the unproved one-poll guarantee and dependency availability (A12-R2-02). The Jan 9 preparation date is conditional on a Jan 23 closure, not a general deadline if closure is earlier. State dates in UTC and distinguish latest permitted stops, last actual acceptance, conditional terminal time, publication and successor opening.

The adopted resolution requires the gap to be stated plainly **in the contract and to clients** (`docs/reviews/amendment-12/DISPOSITION.md:34-37`). A12 says clients are told dates, citing L1's generic closure announcement, but neither changes the contract nor explicitly requires that announcement to explain the successor acceptance gap. For example, a notice announcing only old closure satisfies L1 without telling clients when or why successor acceptance resumes. Register a concrete contract/client communication duty. The already adopted gap itself is not an open author choice.

## A12-R2-07 — LOW: vector outcomes need controlled independent inputs

The window and chain-order predicates in `docs/phase-0-prereg-amendment-12.md:116-126` match the frozen implementation (`service/verifier/tessera_verify/verify.py:283-289`), subject to all earlier checks and input dependencies. “Other window's record or commit → rejected (authority mismatch)” bundles two different mutations: replacing the DNS record while retaining the old commit can trigger `DNS_KEY_MISMATCH` and `CHANNEL_VALUE_MISMATCH`; replacing only the commit can also fail its tree/path, signature or anchor before channel comparison. Construct each vector with internally valid substituted snapshot or commit, matched proof/headers and all unrelated checks passing, and specify the expected first reason or explicitly require only non-acceptance. Likewise isolate `ISSUANCE_WINDOW` from other failures. These are prospective vectors; the draft does not report them as executed.
