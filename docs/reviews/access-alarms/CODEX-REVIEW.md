# D1–D4 access alarm findings

- **MEDIUM — The stage can omit the very rejections D1 and D3 depend on.** `service/issuer/infra/main.tf:480–488`, `service/detect/infra/access.tf:22,36–41,56,65,85`, `docs/V1-DETECTION-CONTRACT.md:68–70`. The stage comment promises one line for every call. AWS documents that API Gateway can omit logs for excessive 429s, gateway 413s and 431s. A flood can return 50 or more 429s while fewer than 50 `THROTTLED` lines reach CloudWatch. An oversized request rejected by the gateway can likewise produce no line, or a 413 line without an attributed key, which D3 drops. Zero defaults apply when logs arrive without matches. Missing data is treated as nonbreaching when CloudWatch needs to fill missing datapoints. Neither supplies evidence of a rejected request. Bound the claim to observed, attributable log events and remove the one-line-per-call guarantee. [AWS guidance on missing REST API logs](https://www.repost.aws/knowledge-center/api-gateway-missing-cloudwatch-logs), [CloudWatch missing data](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-missing-data.html)

- **MEDIUM — D2 can report route mistakes as key guessing.** `service/detect/infra/access.tf:23`, `service/issuer/infra/main.tf:431–445,487–488`, `docs/V1-DETECTION-CONTRACT.md:69`. A client with a valid credential that repeatedly calls a retired route or uses the wrong method can produce 50 logged `MISSING_AUTHENTICATION_TOKEN` responses in five minutes. That is a documented gateway response for unsupported methods and resources, so the alarm alone cannot establish what key the caller sent. Both alternatives match their exact response-type strings. Of five existing stage lines sampled, four matched D2 and both error types were represented. Keep the first alternative for the key rejection signal and qualify or rename the combined signal if retaining the second. [API Gateway response types](https://docs.aws.amazon.com/apigateway/latest/developerguide/supported-gateway-response-types.html)

- **MEDIUM — D3 narrows “any one key” to the configured invitations and observes HTTP responses only.** `service/detect/infra/access.tf:60–70,74–85`, `service/issuer/tessera_issue/api.py:24–25,75–76,85–96,115–120,133–152`, `service/issuer/tessera_issue/lambda_app.py:98–123`, `docs/V1-DETECTION-CONTRACT.md:70`. A valid usage-plan key absent from Terraform can send five submissions with invalid request UUIDs and receive five 400s without contributing to D3. A listed key is counted for a logged 400 or 413 bearing its ID. The Lambda returns 400 for `BAD_REQUEST` and 413 for `TOO_LARGE` on submission, including a repeat of a stored oversized refusal with the same content. Five such repeat responses can count while there is only one REFUSED record. No D3 filter reads `REQ#` or checks the refusal reason. If “malformed” includes reusing a request UUID with different bytes, five such submissions return 409 and count zero. Other 4xx responses can mean closure or window policy, so blanket 4xx matching would change the signal. State the specific statuses, subjects and response-count semantics, or add the missing coverage.

- **MEDIUM — The invitation record named by D4 does not drive the alarms.** `docs/V1-DETECTION-CONTRACT.md:71`, `service/detect/infra/access.tf:9–16,25–27,89–113`, `service/issuer/infra/main.tf:537–545`. The checkout has no `config/invitations.json`. Detection uses the Terraform map of key IDs, names and daily counts, while issuer usage-plan membership is managed separately. If the pilot key is replaced in the issuer and the detection map is left stale, the replacement's first logged 202 raises unknown-key success and its logged requests never accrue against the pilot's daily limit. The current working tree also sets the pilot threshold to 10 in Terraform while the draft says 5. Six requests in 24 hours therefore fail to alarm with the Terraform defaults, and the first breach is at 11. Tie the detection inputs to the invitation record or describe the actual input and its update dependency.

- **LOW — The quota alarm's description claims more than its signal.** `service/detect/infra/access.tf:24,48–55`, `service/issuer/infra/main.tf:530–534`, `docs/V1-DETECTION-CONTRACT.md:71`. If the best-effort usage plan lets a key make request 101 without returning `QUOTA_EXCEEDED`, the quota alarm sees zero even though the nominal daily limit is 100. [API Gateway response types](https://docs.aws.amazon.com/apigateway/latest/developerguide/supported-gateway-response-types.html), [Usage plan quotas](https://docs.aws.amazon.com/apigateway/latest/developerguide/api-gateway-api-usage-plans.html)

- **MEDIUM — The alarm settings support threshold transitions, with no end-to-end email deadline.** `service/detect/infra/access.tf:22–27,37–41,45–57,66–86,94–114`, `service/detect/infra/main.tf:57–60`, `docs/V1-DETECTION-CONTRACT.md:12–17,63–71,89–93`. The one-period sums are D1 and D2 ≥50 in 300 seconds, D3 ≥5 in 3,600 seconds, D4 quota and unknown success >0 in 300 seconds, and D4 volume > the invited count in 86,400 seconds (pilot alarms at 11 with the current Terraform default). CloudWatch's default sliding windows evaluate every minute at these periods, including exactly 86,400 seconds. D3 and D4 need not wait an hour or a day. Define daily as trailing 24 hours: six pilot calls before midnight and five after can breach the configured limit even though neither calendar day exceeds ten. The 10-minute D1/D2 and 15-minute D3/D4 figures can be measured from the qualifying threshold crossing with timely ingestion and delivery. A delayed 50th event can age out of the same five-minute window as the earlier events. A second `QUOTA_EXCEEDED` while already in ALARM produces no new SNS action. A pending subscription produces no email even when the alarm publishes. Qualify the figures as targets for a new ALARM transition under the stated delivery conditions. [CloudWatch alarm evaluation](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation.html), [Sliding evaluation windows](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarm-evaluation-window.html), [Alarm actions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/CloudWatch_Alarms.html)
