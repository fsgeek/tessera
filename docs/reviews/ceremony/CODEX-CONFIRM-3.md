## F01 — raw policy survives; expected spelling is wrong (MEDIUM)

**Lines 169–176,284–285.** Yes: `SCD GETATTR UIF-1` bypasses the lossy `gpg --card-status` parser and conveys the DO D6 value without collapsing 0/1/2. No: for bytes `02 20`, the inspected status serializer prints **`S UIF-1 %02+`**, not `%02%20`. This is reversible status encoding, not literal unescaped bytes.

The source chain, using upstream GnuPG tag `gnupg-2.4.8` (also inspected the corresponding 2.4.4 path):

- [`scd/app-openpgp.c:1175–1177`](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L1175-L1177) maps UIF-1/2/3 to D6/D7/D8 with special handling zero. At [1290](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L1290), `get_one_do` obtains the value; the default branch at [1413–1416](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L1413-L1416) passes `value,valuelen` to `send_status_info`. No boolean conversion occurs.
- [`get_one_do`, lines 613–692](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L613-L692), extracts the DO content from its enclosing object or retrieves the individual object; it preserves content and length. This can use the scdaemon cache, so “raw” does not mean a mandatory direct APDU on every call. The setter invalidates its cache before writing at [3117–3121](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L3117-L3121); cache removal also follows the enclosing tag at [570–576](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/app-openpgp.c#L570-L576). The ordinary set-then-get sequence is intended to reread card state.
- [`scd/command.c:2625–2641`](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/scd/command.c#L2625-L2641) percent-escapes control bytes and literal plus/quote/percent, but encodes a space byte as `+`. Thus `02` becomes `%02`, and `20` becomes `+`.
- [`agent/call-scd.c:1139–1155`](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/agent/call-scd.c#L1139-L1155) forwards this status without policy interpretation. [`tools/gpg-connect-agent.c:2217–2235`](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/tools/gpg-connect-agent.c#L2217-L2235) prints status and OK lines. It does not turn the plus into `%20`.
- [`g10/card-util.c:2250–2260`](https://github.com/gpg/gnupg/blob/gnupg-2.4.8/g10/card-util.c#L2250-L2260) sets `permanent` to first byte `0x02`, `on` to `0x01`, `off` to zero, and the second byte to `0x20`.

Expected relevant successful output after setting permanent:

```
S UIF-1 %02+
OK
```

Rehearsal 2 should record the complete command output, Tails/GnuPG/scdaemon versions, setter errors if any, and the identity of C. A successful raw result decodes to `02 20`; `%01+` or `%00+` fails the required policy. ERR, missing/empty UIF status, malformed/unexpected length or bytes also leave confirmation unestablished: stop and investigate. If the actual stack prints `%02%20`, that contradicts this inspected serializer's spelling prediction, although a correctly decoded value would still be `02 20`; identify the actual version/patch before changing the documented expectation. A no-touch signature succeeding falsifies enforcement even with a nominal `02` readback. A correct readback alone does not establish PIN policy, trusted firmware or host integrity.

Disposition: **the previous HIGH loss-of-distinction defect is resolved at source level; actual-stack confirmation remains pending.** Correct line 174 before rehearsal. Because line 175 tests the first byte, the spelling error does not by itself authorize accepting ordinary touch as permanent; it can confuse or stop a correct run. These two inspected tags do not establish behavior of every 2.4 release or downstream build.
