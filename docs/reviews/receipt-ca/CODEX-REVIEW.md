# Content-addressed receipt objects · Codex review · 2026-11-22

## HIGH — The production API cannot reach the legacy fallback

`service/issuer/tessera_issue/api.py:182–185`, `service/issuer/tessera_issue/aws.py:38–40,286–292`, `service/issuer/infra/main.tf:204–217`

A client retrieves its unexpired COMPLETE receipt from before the deployment. The correct bytes are still at `result/<rid>/receipt.json`. The new API first issues HEAD for the absent digest-named object. Its role has GetObject on results, with ListBucket limited to the content prefix. S3 returns 403 for the absent result key under those permissions. The adapter propagates 403, so the Lambda raises before probing the intact legacy object. The client gets an API Gateway 502 instead of a 303. Status lookup can still show COMPLETE. This breaks S5's 30-day retrieval duty for every fixed-key-only receipt under the checked-in IAM policy. [AWS HeadObject permissions](https://docs.aws.amazon.com/AmazonS3/latest/API/API_HeadObject.html) · [API Gateway Lambda error handling](https://docs.aws.amazon.com/lambda/latest/dg/services-apigateway-errors.html)

A local probe through the real adapter and Lambda handler reproduced the exception with a matching legacy object and an S3 double returning the documented 403. The 76 tests across the four changed test modules passed. The fallback test uses the in-memory store (`service/issuer/tests/test_receipt_content_address.py:51–58`, `service/issuer/tessera_issue/local.py:69–71`). FakeS3 also returns 404 on every HEAD miss (`service/issuer/tests/fakes.py:153–156`). Either double lets the fallback run. The same missing-key handling can produce a 502 when a result disappears between the state check and the S3 probe, where the new design describes a 410. Production IAM behavior here was inferred from Terraform and AWS documentation.

## MEDIUM — The legacy hash check covers the API's read only

`service/issuer/tessera_issue/api.py:182–189,205–215`, `service/issuer/tessera_issue/aws.py:230–231,294–296`, `service/issuer/DESIGN.md:289–293`

If the fallback is made reachable, the API hashes the correct fixed-key bytes and mints a URL for that key. A delayed PUT from a pre-change worker can replace the object after the check, either before the first S3 GET or between uses of the same URL. A URL minted by the old API before deployment has the same exposure during its remaining lifetime. The submitting credential can thereby obtain a full body that differs from the durable COMPLETE digest. The client can detect the mismatch by hashing the body against the 303's `Tessera-Receipt-SHA256` as S2 requires (`docs/V1-SERVICE-RESOLUTIONS.md:21`). The header does not prevent delivery. If the overwrite has already happened when the new API hashes the fixed-key body, it returns 410 and cannot recover the original from the unversioned bucket (`service/issuer/infra/main.tf:89–93`). This residual requires a different-byte write to the fixed key while a legacy URL is usable. An API client credential alone has no result-object write path. [S3 presigned URL reuse](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

For digest-named objects, the poller computes the name from the exact bytes it writes and records that same digest in the guarded COMPLETE (`service/issuer/tessera_issue/pipeline.py:270–274,1301–1308`). Under SHA-256 collision resistance and the issuer write paths, a delayed different-byte write goes to a different key, and a same-name retry writes identical bytes. Deletion can make a subsequent GET fail. A principal with direct result-write privileges can still overwrite the checked name after the API reads it, since the URL binds the key alone. The stale-worker guarantee depends on the writer following the digest naming rule.

## MEDIUM — The API now downloads the entire receipt before redirecting

`service/issuer/tessera_issue/api.py:183–186`, `service/issuer/tessera_issue/aws.py:233–246`, `service/issuer/tessera_issue/deadline.py:73–78`, `service/issuer/infra/main.tf:341–349`

A successful retrieval now adds an S3 GET and SHA-256 pass after HEAD. For a typical roughly 5 MB receipt (`service/issuer/DESIGN.md:78–79`), each invocation buffers roughly that much additional data. The API ignores the HEAD size and reads the whole body in one call, so peak memory grows with stored object size. The request input limit does not bound assembled receipts, which also carry frozen material and evidence (`service/issuer/tessera_issue/api.py:134–135`, `service/issuer/tessera_issue/pipeline.py:1321–1338`). A slow or retrying GET can exhaust the 29-second Lambda budget even when HEAD and URL generation would have succeeded. The poller deadline is inactive in the API, and the SDK permits three attempts with 3-second connect and 8-second read timeouts (`service/issuer/tessera_issue/service.py:21–24`). No evidence from this review shows that normal receipts approach the 512 MB limit.

Success still sends 303 with `Location`, `Tessera-Receipt-SHA256`, and `Cache-Control: no-store` (`api.py:213–215`). Digest mismatch now returns 410 even for an unexpired record (`api.py:185–189,207–209`). The Lambda and gateway logging fields omit the minted URL (`service/issuer/tessera_issue/lambda_app.py:68–76,89–95`, `service/issuer/infra/main.tf:475–482`).

## INFO — Expiry gates minting, and cleanup covers both key shapes

`service/issuer/tessera_issue/api.py:155–167,197–215`, `service/issuer/tessera_issue/pipeline.py:373–395`, `service/issuer/tessera_issue/aws.py:248–284,294–296`

The API returns 410 for expired records and 409 for unexpired REFUSED records. A second clock check after object reads prevents a fresh URL if the request expires during the read. A different credential gets a different record ID (`api.py:38–43,160`). A URL issued a second before expiry remains usable for its remaining lifetime of up to 300 seconds if the object still exists and the signing credentials are valid. For example, when the poller has yet to delete the object, the API can return 410 while the previously issued URL still works. This is existing behavior for both key shapes, within the stated service timing tolerance under its assumptions (`docs/decisions/2026-10-27-service-clock-tolerance.md:26–30`). A refused request never had a durable COMPLETE from which to mint a URL. A completed cleanup removes the target, so a subsequent GET using an outstanding URL fails unless a writer recreates the key. [S3 presigned URL expiry](https://docs.aws.amazon.com/AmazonS3/latest/userguide/using-presigned-url.html)

The production S3 adapter tags, deletes, and checks for survivors under the whole `result/<rid>/` prefix. A request with a fixed-key object, a committed digest object, and a losing worker's digest object has all three selected once result cleanup is due. The tag listing paginates, and deletion relists the first page after each batch. A per-object error, round limit, or survivor retains the obligation for retry. The writer lease and final empty listing still govern discharge. A write that lands after the final empty listing and outside the assumed writer window could survive discharge, as could a new direct S3 write. The test at `service/issuer/tests/test_receipt_content_address.py:73–85` exercises both names through the real adapter with fake S3.

S5 supplies the retrieval duty, but the reviewed signed text supplies no fixed-key exception. Making the fallback operable would leave this conflict for an author ruling. S2 still requires the client digest check for every completed result (`docs/V1-SERVICE-RESOLUTIONS.md:21`), so DESIGN's “for those receipts only” wording is also too narrow (`service/issuer/DESIGN.md:292–293`).
