## Migration

- **Overwrite — yes.** The existence probe and PUT are separate, with no create-only condition passed to the write. Two overlapping runs can both see a miss, and the later PUT replaces the first copy even when the bytes are identical. An intervening write by another principal is also replaced. The tool has no write to the fixed-key source. (`service/issuer/tools/migrate_receipts.py:21–22,29–39`)
- **Delete — no.** The tool has no delete call. It can recreate a digest object after cleanup if it reads the COMPLETE row and matching legacy bytes before cleanup, then reaches PUT after cleanup removes the objects. It has no expiry check or coordination with cleanup. (`service/issuer/tools/migrate_receipts.py:20–39`, `service/issuer/DESIGN.md:288–289`)
- **Copy bytes that disagree with COMPLETE — no for the record read, under SHA-256 collision resistance.** The tool hashes the bytes it fetched and writes those same bytes. If a stale worker changes the fixed key after the read, the write still uses the verified buffer. If the digest destination already exists with wrong bytes, the tool reports `present` based on size alone and leaves it there, even when the correct legacy body is available. A client applying S2 still cannot retrieve an acceptable receipt in that case. (`service/issuer/tools/migrate_receipts.py:21–39`, `service/issuer/tessera_issue/api.py:179–180,197–205`)
- **Miss an unexpired pre-change receipt — yes.** Each run lists fixed keys, then reads each row once. A legacy worker can have uploaded the correct fixed-key body before the post-deploy pass, still be in progress when the tool reads its row, then commit COMPLETE after the tool reports `not-complete`. Both passes can finish successfully, with the receipt stranded at its legacy key. A fixed key created after the last enumeration is also invisible to the tool. `missing` and `not-complete` do not affect the exit status. Two passes cover this only if the final pass starts after legacy writes and their COMPLETE commits have drained. A stale overwrite before either pass can also destroy the matching legacy bytes, in which case the tool reports `mismatch` and cannot recover them from the unversioned bucket. The `DEPLOY-RUN` text supplies no run results or evidence of drain within this commit. (`service/issuer/tools/migrate_receipts.py:20–32,43–50,65–70`, `service/issuer/DESIGN.md:282–284,291–293`, `service/issuer/tessera_issue/api.py:175–176`)
