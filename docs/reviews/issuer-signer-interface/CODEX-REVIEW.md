Reviewer: Codex. Date: 2026-10-30. Base commit: `8bcfcdaf8b5451158f8515ebdb3e583082740699`, plus the five working-tree files represented by `FIX.diff`.

## Findings

### ISI-01 — Low: GCP integration coverage still substitutes the frame-path producer

Location: `service/signer-gcp/tests/test_issuer_protocol.py:17-23,34-63`; `service/issuer/tests/test_review_fixes.py:379-391`.

The GCP round trips run the real `SlotSigner` and real GCP signer, but their `stash_into` constructs `frames/rid-7/<digest>` itself. They do not invoke `pipeline._send`, `st_frames`, `drain`, or `_seal`. The new issuer regression checks a copied regular expression against stand-in requests, rather than calling the GCP consumer. A future GCP-only change that rejects the issuer's 64-hex request namespace while continuing to accept `rid-7` could pass both groups of tests and refuse every large real request. A GCP manifest-policy change could similarly reject actual pipeline manifests while accepting the independently constructed fixture.

This is a coverage finding, not a currently failing production scenario. The KMS package already has full pipeline issuance coverage for inline and 1 MiB content (`service/signer-kms/tests/test_roundtrip.py:73-93`). Thus “no test runs them together” is too broad for the current tree: KMS does; GCP runs the shared interface but substitutes the upstream producer.

Recommendation: retain a GCP pipeline test, ideally running both production signer classes together with fake provider clients, for inline and by-reference issuance. Retain a late-response/next-attempt case as well. The scratch probe ran both production signer classes through the real pipeline successfully for 20-byte and 1 MiB content. That supplies present review evidence but does not close the retained regression gap.

### ISI-02 — Medium, pre-existing: implementation compatibility is not registered conformance

Locations: `formal/p8/HYBRID-SUPPLEMENT.md:170-176`; `service/signer-kms/infra/main.tf:54-74`; `docs/phase-0-prereg-amendment-11.md:3-10,240-250`; `service/issuer/tessera_issue/pipeline.py:46-49`; `docs/phase-0-prereg-amendment-2.md:260-289`.

The registered K-R enforcement text grants signing only to the **issuer role**; the implementation grants it only to the dedicated **signer role** and denies others. The proposed wording repair is in unsigned Amendment 11. Concrete consequence: applying the current signer policy does not implement the registered principal placement, even though the two packages interoperate and the signer policy restricts signing inputs. Passing these suites cannot adopt that amendment.

Separately, permanently incomplete evidence leaves an attempt open in the current gated lifecycle, while A2.3 retains an implementation termination obligation. A calendar that never supplies evidence is a concrete example. The design explicitly discloses this unresolved conflict (`docs/decisions/2026-10-29-issuance-lifecycle.md:140-146,189-196`). The reference fix neither introduces nor resolves it. Amendment 11 explicitly does not accept the lifecycle residual (`:287-295`). These are registration/claim limits, not reasons to restore attempt-prefixed frame names.

## A. Why the fix is sound

- **Object identity:** `_send` now writes `frames/<rid>/<sha256(frame)>` (`pipeline.py:584-596`), matching `ResultStore.ref` (`stores.py:125-136`), KMS's strict reference grammar and filename/digest equality check (`signer.py:152-165`), and GCP's accepted grammar plus fetched-byte digest check (`policy.py:87-92`; `signer.py:130-149`). Here and below, signer filenames are relative to their respective package unless stated otherwise.
- **Isolation is elsewhere:** `st_frames` derives signer IDs from request **and attempt**, slot and frame hash; it persists an index containing the attempt and job before sending (`pipeline.py:653-674`; `signers.py:31-34`). Work frames remain `work/<rid>/<aid>/<frame>`. Signature objects remain `work/<rid>/<aid>/sig-<job>-<signature-digest>` (`pipeline.py:512-535`). None of these paths changed.
- **Equal bytes are safe to share:** different declarations normally change attestation bytes, but distinct attempts allocated in the same second can have equal declarations. The manifest is identical across attempts in any event. Isolation does not depend on all attempts having different frame hashes: the attempt remains in the signer-request scope even for equal frames. Hash naming provides content identity, not an attempt identifier. This relies on SHA-256 collision resistance and trusted storage/writers.
- **Retries and late replies:** unanswered jobs reuse their IDs (`pipeline.py:688-703`). A late response for the current job can satisfy it; a response indexed to a previous attempt is logged `other-attempt` before it can supply a signature or trigger refusal (`:479-500`). Duplicate current-job responses do not replace the selected signature (`:491-495`). GCP caches signatures only by `(request_id, frame digest)` within one run (`signer.py:62,168-185`); across runs and in KMS randomized signing may yield another signature. The issuer's digest-named signature objects and guarded adoption handle that.
- **Sealing:** `_seal` reads the attempt's work frames and selected signature objects, checks signature digests, verifies signatures on exact frames, and requires the durable used-log entry (`pipeline.py:706-734`). It does not consume frame-reference names. The trusted-storage limitation and poisoning stall recorded in `CODEX-CONFIRM-10.md` remain unchanged; a digest-looking name is not cryptographic verification by itself.
- **Cleanup and `mark_due`:** `END_NS` includes `frames`; `_cleanup_one` first checks persisted request termination, tags and deletes the whole request namespace, and keeps the obligation through the late-writer lease (`pipeline.py:304-340`). There is no per-attempt frames deletion. S3 listing/tagging uses `frames/<rid>/` and the actual returned object names (`aws.py:224-231,267-284`). Repeated puts of identical bytes can replace the object and remove old tags, but active requests have no cleanup-due tags; after termination the retained cleanup obligation repeats tagging/deletion for late writes. This behavior does not need an attempt prefix.
- **Infrastructure:** the relevant grants use `frames/*`; the result lifecycle uses the cleanup-due tag, not an attempt filename (`service/issuer/infra/main.tf:96-129,316-319`; `service/signer-kms/infra/main.tf:111-115`). GCP has no `infra/` directory; its AWS access comes through the issuer role and `deploy.sh`, detailed below. No inspected rule requires the dropped prefix.

### Infrastructure permissions and configuration

The poller writes frame objects, sends each slot's requests, and receives/deletes responses (`service/issuer/infra/main.tf:237-262`). The API does not need signer-queue or signing grants. Result-bucket encryption is AES256 (`aws.py:231`), so the reference-read design does not require a separate SSE-KMS decrypt grant.

KMS Lambda role: `service/signer-kms/infra/main.tf:100-115` grants request Receive/Delete/GetQueueAttributes, response Send, and GetObject on `${frames_bucket}/frames/*`. `FRAMES_BUCKET` is supplied in `:16-22`, consumed by `lambda_app.py:68-69`. Its event source reads the issuer's kms request queue (`:151-155`). It does not need the issuer's remote signer-role assumption; the KMS README explicitly excludes `kms` from `signer_principals` (`:53-54`).

GCP: there is no `service/signer-gcp/infra/`. `deploy.sh:108-131` constructs the Google web-identity federated role and its permission to assume the issuer's gpg signer role; `:139-142` configures both roles, queues and FRAME_BUCKET. The issuer's `signer_principals` trust and policy (`service/issuer/infra/main.tf:289-319`) supply per-slot request/response access and GetObject on `${results_bucket}/frames/*`. Runtime assumes the configured roles before use (`service/signer-gcp/tessera_signer/main.py:87-95`). GCP's HSM IAM is separate from AWS frame access.

**Repository grants agree with the read paths.** None grants signers object writes or depends on an attempt-prefixed name. They are source inspections backed by static infra/adapter tests, not an applied-plan or live-principal proof. Bucket, role, queue, pinned key/creation time and SIGN_UNTIL still have to be wired consistently at deployment; no test establishes that those deployed values match the issuer window.

## C. Harness changes

The unpacking edits discard only the new age key; they retain status, signature verification, duplicate-signature identity and queue-empty assertions (`service/signer-kms/tests/test_roundtrip.py:64-70`; `service/signer-gcp/tests/test_issuer_protocol.py:26-27,76-84`). They do not change signer response handling or signer retry thresholds.

GCP `QueueView.receive` now requests the real count from FakeSqs and places it in the issuer's Message (`tests/fakes.py:93-99`). FakeSqs increments and returns the count only when requested (`:50-62`). This strengthens fidelity; it does not hard-code every delivery as first. The scratch check deliberately omitted acknowledgement and advanced past visibility: receives changed **1 → 2**. None of the old receive-count cases was removed. Remaining limitation: sent=None and seq=0 mean this test wrapper cannot test cross-slot oldest-first order; that was not previously covered by these tests either.

## Validation and conclusion

Executed `.venv/bin/python -m pytest -q` separately in all four package directories. Results: issuer **235 passed** (133.25 s); signer-kms **48 passed** (14.96 s); signer-gcp **118 passed** (0.47 s); verifier **135 passed, 77 subtests passed** (47.39 s). No suite failures or skips were reported. The scratch probe uses both production signer classes with the real issuer local pipeline and its TEST window keys, while replacing provider clients and queues. Both sizes reached COMPLETE through actual pre-ship checking, and both GCP attestation and manifest were signed. This is local execution evidence; it does not establish deployed code identity, live IAM, model refinement, general liveness, or registration adoption.

The fix is appropriate to keep. No regression was found in attempt isolation, frame binding, cleanup, signature storage, or harness receive counts. Retain the GCP pipeline integration coverage to prevent the same defect class from recurring, and keep the existing registration decisions separate from this functional confirmation.
