# Adversarial review of RESOLUTIONS-DRAFT — 2026-10-14

**Disposition: revise before owner adoption.** The draft closes substantial gaps, but does not yet determine one full verifier. Its blanket claims that every change avoids amendment, that every CLARIFY is merely clarification, and that no signed bytes change are too strong. There is no demonstrated end-to-end forged receipt here: there are concrete rule-level counterexamples, a conditional trust-distribution attack, and reproducible codec/policy divergences. These distinctions matter.

Authority for this review is Amendment 9, as instructed, despite its PROPOSED status. The owner still decides the resolutions before 30 Oct; this review decides none of them. A9 outranks the profile and the draft. Read in full: RESOLUTIONS-DRAFT, GAPS, A9, V1-PROFILE, ENCODING-V1. Prototype reads were used to check artifact claims, never to supply missing normative rules. Existing workspace changes were left alone. Only this review file was written.

Severity: **Critical** means a conditional path to fabricated service receipts; **High** means a load-bearing claim, registered outcome or freeze decision is wrong or unresolved; **Medium** means a remaining implementer/verdict fork or an unjustified acceptance restriction; **Low** means a bounded wording or evidence-accounting defect. “No attack found” below is not a security proof. Constructed header schedules are admissible-condition examples, not fabricated historical mainnet pins or executed Bitcoin attacks.

## Findings and exact fixes

### F01 — High: G02 does not establish “before the receipt”; its CORRECT still overclaims

**Location:** draft §D/G02, lines 438–458; §B/G03; E §7.1; A9 C4/C5 and A9.6 chain-time residual.

`T_git <= declared_issue_time` is precise as a numeric comparison. It is not proof that the assertion was pre-committed before receipt creation, or even before the receipt's anchor in chain order. The receipt can have `T < declared` by ε, while git can have `T_git = declared`. Moreover Bitcoin nTime is not monotone and establishes no UTC lower bound. Calling this the “stricter” choice than `T_git <= T` is wrong for `T < declared`: those rules are incomparable over A9's allowed domain.

**Distinguishing input:** an honestly signed receipt declares 12:00, anchors at height h with nTime 11:55, and obtains its five successors in time. Its declaration is within the signer's ε check. A subsequently manufactured signed assertion anchors at height j > h with nTime 11:59, during the configured repository-key interval. A DNS snapshot anchors at 12:10 with valid witness windows. Use the same genuine receipt keys, matching channel values, and a window containing declared and T. Every proposed temporal comparison passes, although the git assertion was made after the receipt existed and after its inclusion block. A9's channel-capture adversary can manufacture the authority evidence after capturing the relevant channel credentials, while retaining the uncompromised service's original signatures. This is a counterexample to the proposed pre-commitment explanation, not a forgery of those signatures or a demonstration of key reattribution. Capture of both authority channels is the premise of this version of the construction.

The DNS correction is appropriate: DNSSEC at T_snap does not establish publication before issue. The replacement must not transfer that unsupported chronology claim to git. Waiting for git k=6 before honest issuance helps operationally but is not enforced by the proposed comparison and does not prove UTC ordering to a verifier. Equality also does not mean “before.”

**Exact proposed fix:** retain the numeric check if the owner chooses it, but replace the CORRECT text with:

> The same window value is authenticated by the anchored git assertion and by DNSSEC at the snapshot's own anchored time. The verifier requires T_git <= declared_issue_time. This is a chain-time comparison with a signed declaration; it does not establish UTC ordering or that the git assertion predates the receipt anchor. Before honest issuance the issuer obtains and validates the git assertion's k=6 proof.

If C4's “pre-committed” is intended to mean an externally checked prior authority commitment, also require `h_git + 5 < h_receipt` on the pinned mainnet history and call that **chain-order pre-commitment**, expressly retaining A2.1's UTC limitation. This additional rule needs owner selection and honest-path boundary vectors; it is not already in the draft. If “pre-committed” promises actual pre-issue chronology, author correction/amendment of that registered claim is necessary unless a binding to previously established authority evidence is introduced. Such a binding can change signed frames and P8 vectors. Merely editing E, which A9 incorporates at its signing baseline, cannot evade this decision.

**Label:** split CORRECT (withdraw chronology overclaim), new owner profile restriction (the comparison), and issuer practice (wait for k=6). Do not label the whole package CLARIFY. No honest shipped V1 counterexample to the wait-first revised issue path was found, but “ships complete” alone does not imply wait-before-sign.

### F02 — High: G05's pruning argument is sound only within a stated coverage contract

**Location:** draft principles 2, §B box and G05, lines 240–251 and 287–301; A9.1 C6 and the header-pin rule; P §7.2.

There is no new cryptographic false accept merely from ignoring a missing-header branch while a real, digest-linked, depth-6 pinned branch qualifies. Removing the missing branch gives the same selected witness. A9 expressly makes T presentation-sensitive. Requiring all attestations to verify cannot prevent a presenter from pruning them. On that bounded question, the draft's argument survives adversarial review.

It does **not** imply that contradictory evidence becomes harmless, or that A9's coverage outcome can be changed without identifying the change. A proof with qualifying h and an attestation q beyond the pin horizon, but no headers at q, receives VALID_STRICT under G05 if everything else passes. A9 says “Anchors beyond the newest pin are UNVERIFIABLE”; it also says every **bundled header** must be pinned. The latter is clearly respected; whether the former quantifies over selected anchors or all presented Bitcoin attestations is unresolved. The draft chooses selected anchors. That is a possible reading, not evidence that no registered sentence is implicated.

**Remaining fork:** “Broken linkage among bundled headers” does not say whether only required adjacent pairs, all adjacent heights in the shared pool, or a missing intermediate height counts. At q, a present correct pinned inclusion header with missing successors is ignored; a present unpinned inclusion header blocks the whole bundle. Implementers need that asymmetric rule explicitly. A q branch with no headers cannot be called a verified forgery; the proof carries an unverified assertion only.

**Exact proposed fix:** add:

> Attestation selection is existential over qualifying branches. A syntactically valid Bitcoin attestation without a complete h..h+5 segment is nonqualifying, not a required failed check. It supplies no time or trust fact. All supplied headers, including unused ones, are independently checked against pins. For each adjacent supplied pair at consecutive heights, the prev-hash link must match. Missing heights are not a broken-link failure. The selected anchor, rather than every unverified attestation, is the referent of “anchors beyond the newest pin.”

Obtain an explicit owner reading of A9's C6 sentence; if its intended meaning was universal coverage, record an amendment/correction, rather than silently overriding it. Add conformance cases for a qualifying branch plus absent-q headers, partial-q headers, unpinned-q headers, a contradicted q branch, and pending-only proof. A genuine upgraded proof containing a complete valid original witness should pass when new branches lack headers. No NARROW-MODEL follows from pruning alone; treating this as a loss of cryptographic protection would overstate what all-branch verification can protect.

### F03 — High: G03 changes verdicts on nonmonotone nTime; “earliest” needs a registered reading

**Location:** draft §B/G03, lines 256–273; A9 C5; E §7.1.

Lowest height is deterministic once qualification is fixed. It is not equivalent to lowest timestamp. Let two qualifying attestations have h1 < h2, `nTime(h1) = not-after + 1`, and `nTime(h2) = not-after`. Both depth segments and all other comparisons can pass. G03 gives ISSUANCE_WINDOW; smallest-nTime gives VALID_STRICT. Reverse the boundary relative to `declared - epsilon` and the acceptance direction reverses. Nonmonotone nTime is allowed without a deep reorganization or hash break.

This is not a demonstrated unsafe accept under A9: A9's undefined “earliest” is the issue. Pruning reproduces either selected attestation but does not make two different algorithms identical on the **same declared input**. “Smallest nTime mixes blocks” is not a valid objection: that implementation can take both T and confirmed_at from the attestation selected by smallest nTime.

**Exact proposed fix:** replace the flag/rationale with:

> Earliest means lowest Bitcoin block height among qualifying attestations, not least nTime. Both T and confirmed_at come from that selected segment. Nonmonotone timestamps can make another selection rule return a different verdict on the same proof. This profile fixes the chain-order reading of A9 C5.

Have the owner confirm that reading against the registered C5 sentence; amend if chronological minimum was intended. Add nonmonotone two-branch tests at c1, c2 and not-after, and one test with both branches at the same height. No signed layout or existing P8 vector must change for this reading. The draft's “up to about 2 h” should be removed as a bound on nonmonotonicity: the forward-clock check does not establish that general bound.

### F04 — Critical conditional attack; High unresolved assumption: G08 needs independent configuration authorization, not just another key

**Location:** draft §C/G08, lines 332–364; A9 adversary, C4/C6, A9.5; P §5.

The key finding is correct under its stated deployment condition. If a captured repository credential is also an accepted configuration-update signer, an attacker signs a config adding their own root KSK, repository key and header pins. They create service-looking frames and signatures under their own keys, a matching manifest, their own DNSSEC chain and git assertion, and fabricated headers with chosen merkle roots/times. The authentic verifier then accepts fabricated presentation evidence without a service issuance event. Pins no longer represent authentic mainnet. This does not require breaking SHA-256: it compromises the authority deciding which hash is trusted.

Append-only CI cannot prevent this when the verifier accepts any validly signed config and the attacker can bypass CI. Even enforcing append-only at the verifier would not stop adding attacker entries and pins at new heights. Conversely, if config hashes are independently allowlisted in an authenticated release, possession of its detached-signature key alone does **not** suffice. The draft must state which distribution model it means. An unsigned config inside an authenticated, integrity-checked release can be trustworthy; “unsigned implies local edits are accepted” is not generally true.

A distinct key can still be callable using the captured channel account, repository credentials or shared signing service. Key inequality alone does not establish independence. Calling all capture of that key “outside A8.3” without specifying the access boundary introduces an assumption by declaration.

**Exact proposed fix:** add:

> The accepted trust-config authority is authenticated independently of the bundle and of both authority-channel credentials. Capture of any authority-channel credential grants no config signing capability, no ability to authorize a new config hash, and no ability to replace the verifier's compiled trust root or policy catalog. The dated custody record names and verifies that authorization boundary. The verifier accepts only configs authenticated by this declared mechanism; CI alone is not its authenticity check.

Choose either the dedicated-key update model or independent release allowlisting, and specify bootstrap, key rotation, version/genesis values and invalid-config no-verdict behavior. Keep “distribution compromise” as an explicit external assumption, and test a captured repository signer trying to authorize a config. Generating a third token is insufficient evidence by itself.

**Label/amendment:** new trust-distribution design plus explicit assumption, not mere CLARIFY. With genuinely independent authorization this repairs an underspecified trust input and needs no protection concession. If independence cannot be supplied and a channel credential can rewrite distributed trust, then a NARROW-MODEL/amendment excluding that capture path is required. “No NARROW-MODEL needed” is conditional on implementing the boundary, not established by selecting a distinct public key. Config bytes acquire a new signature, although receipt-frame layouts need not change.

### F05 — High: G16's generalized table can omit KSK reliance and misclassify mixed DS evidence

**Location:** draft §E/G16, lines 495–520; G22; A9.5 root rule; P §5's split.

The algorithm allowlist is a legitimate visible NARROW-CLAIM, not a demonstrated NARROW-MODEL. Unsupported algorithms must never become an insecure-but-accepted chain. However, the table “per required RRset” says a supported signature validating at T_snap passes and does not include KSK reliance eligibility. G22 supplies byte equality, not the missing period check. Another implementer will import A9's period rule; a literal implementation of the generalized table can pass a root signed by a trusted retired KSK outside reliance. A captured retired KSK can produce such a signature without breaking its algorithm. A9 governs and forbids this acceptance, so the final text must expressly preserve it.

Mixed DS evidence is another fork. An authenticated DS RRset containing only type 4 gives unsupported under one row, but “no child DNSKEY matches a validated DS” gives INVALID under another. The same fork occurs with a supported nonmatching DS plus unsupported DS material that might match. An unrelated invalid or unsupported candidate must not defeat a supported validating path. No-candidate/missing-RRSIG cases also lack a complete outcome.

The observed root/com algorithm 8 and wamason.com algorithm 13 support the bounded current-chain choice. Dropping instrument support for DS type 4 has no demonstrated security benefit under A9's cryptographic assumptions and can reject honest future chain configurations. Algorithm 13 is already allowed, so a root move to ECDSA P-256/SHA-256 **alone** does not cause the example's unsupported outcome. A new unlisted KSK is a separate trust-coverage problem.

**Exact proposed fix:** prepend:

> The root RRset passes only under A9.5: a byte-matching configured KSK, usable in its reliance interval at T_snap, verifies a selected RRSIG valid at T_snap. G16 never replaces that eligibility condition. Candidate aggregation is existential and order-independent; extra candidates are informational after any eligible supported path passes.

Define DS outcomes explicitly: a supported matching authenticated DS/DNSKEY path is eligible; if no such path exists and an unsupported algorithm/digest could supply the required path, report UNVERIFIABLE/DNSSEC_ALGORITHM_UNSUPPORTED; if all relevant possibilities are supported and checked and none matches, report INVALID/DNSKEY_DS_MISMATCH. Missing necessary RRsets/signatures are unperformable. Preserve P's root reliance/window/crypto reason precedence. Add mixed type-2/type-4, supported+unsupported RRSIG, missing witness, and outside-reliance controls. Replace the rollover example with an actually unsupported algorithm. Record the allowlist as an owner scope choice, with issue-time fail-before-ship handling. No P8 change is required; an amendment is required only if this overrides A9's root rule or registered honest-case scope rather than selecting a supported issuance path.

### F06 — High: G26 early exit violates G31/G32's six-field reproducibility

**Location:** draft lines 708–732; A9.4 stable-field contract.

A failed check makes the verdict INVALID, but does not settle its stable reason or T. On a bundle with both KEY_MISMATCH and a bad git signature, executing git first and stopping reports a different reason from G31's canonical keys-first order. On a bad-signature receipt with otherwise qualifying receipt OTS, one implementation stops before OTS and reports T=null; G32 requires the verified T. The draft permits both schedules. Dependencies on failure can also hide an independently determinable field.

**Exact proposed fix:** replace “may stop early only on a failed check” with:

> Physical evaluation order is unrestricted, but reporting uses the fixed total check order. Early termination is permitted only when every earlier-priority reportable check is settled and every stable field, including T, is determined. A failure prevents only checks whose own necessary input cannot be obtained; it does not suppress independent receipt-anchor evaluation needed for T. Derived checks are unperformable when necessary inputs cannot be obtained, and never pass by default.

Enumerate subchecks and ties within stages, including all missing member paths and per-slot checks. Define T=null for contradictory/unusable receipt anchor evidence, rather than merely “some qualifying attestation” when another receipt branch contradicts it. Add reversed-schedule tests with two failures, unknown alg plus independent failure, and a signature failure plus a usable anchor. No amendment or P8 byte change is needed to satisfy the existing stable-field contract.

### F07 — Medium: G11 is a new signature restriction and its standards rationale is incorrect

**Location:** draft §G/G11, lines 582–605; E §3.5 and §5.2; GAPS G11.

The current codec intentionally does not interpret subpacket contents. RFC 9580 distinguishes **unknown** critical subpackets from recognized critical ones, and recommends marking creation time critical. Banning every critical bit therefore rejects ordinary standards-conforming signatures, including a correctly formed critical creation-time subpacket. It is not forced by the RFC. [RFC 9580 §§5.2.3.7, 5.2.3.11](https://www.rfc-editor.org/rfc/rfc9580.html#section-5.2.3.7).

**Executed distinguishing input:** SIG-01 with the critical bit set on its unhashed key-ID subpacket still passes implementation A's codec and verifies mathematically. G11 rejects it. This is a policy restriction above P8, not a forgery; changing committed signature bytes also requires a new anchor. A newly generated honest signature with a critical creation time has the same policy issue before stamping.

There is also a fork between the top table's “no signature-expiration subpacket” and the body rule's “hashed area holds no … type 3”. Type-2 payload length is unstated: “one creation-time subpacket” could be interpreted as only a type count, admitting a malformed payload. RFC's creation-time payload is four octets; that must be explicit.

**Exact proposed fix:** adopt a small explicit policy: exactly one hashed type-2 subpacket with four data octets; recognize it whether critical or not; reject unknown critical hashed subpackets; state the treatment of each other recognized critical type. Either ignore all unhashed semantics consistently with E §3.5, or visibly choose a new transport/policy restriction and say why. Specify whether type 3 is forbidden in hashed area only and retain the “never wall-clock expiry” rule. If the blanket ban is retained, label it NARROW-CLAIM/new owner signature profile and constrain the issuer adapter before signing/stamping.

Existing SIG-01/02 need not change. Add signature-profile acceptance/rejection vectors distinct from P8 codec vectors; do not change codec expectations merely to impose this policy. More generally “no signed byte changes” must distinguish a new issuer's allowed signature output from an unchanged frame layout.

### F08 — Medium: G19, G24 and G16 disagree on missing DNS groups

**Location:** draft §A/G19, §D/G24, §E/G16; P §5 and §7.3.

G19 requires root DNSKEY, each DS/DNSKEY group and TXT, with one or more RRSIGs per group and order violations INVALID. G24 says absent TXT is UNVERIFIABLE. P explicitly classifies absent root RRset/RRSIG as unperformable. A parseable RR sequence ending before TXT or containing a root DNSKEY without RRSIG has no single outcome under these rules. G19 also says names are RFC 4034 §6.2 canonical, but singles out owner and RRSIG signer names; complete canonicalization of domain-name fields inside RDATA must be stated.

**Exact proposed fix:** distinguish framing from completeness:

> A truncated RR encoding, forbidden RR type, duplicate RR, inconsistent owner/type within a group, or misordered supplied group is INVALID/SNAPSHOT_FORMAT. A syntactically complete sequence lacking a required RRset or its witness RRSIG is UNVERIFIABLE/DNS_EVIDENCE_MISSING (or the root-specific NO_TRUSTED_KSK_USABLE). Missing groups do not alone constitute order violations. All domain-name RDATA fields are encoded canonically under RFC 4034 §6.2.

Define group boundaries using owner, type and covered type, signer-zone/ancestor constraints, root-signer case and the empty/missing sequence distinction. Keep explicit no-wildcard scope as NARROW-CLAIM. Conversion from resolver messages changes snapshot body S and SHA256(S), so previously stamped JSON snapshots cannot be reused. It requires a fresh snapshot stamp, although P8's envelope construction and existing vectors need not change. No documented conforming explicit-owner V1 receipt is shown falsely rejected after fresh capture/conversion; the archived spike is not already a conforming V1 bundle.

### F09 — Medium: G20's “first double SHA256” need not be a transaction id

**Location:** draft §A/G20, lines 194–222; E §5 outside-preimage list; registered R-3.42/R-3.43 as quoted by draft.

The repository corpus supports the claimed calendar convention, not a theorem about every accepted proof. Construct a valid proof that first computes `SHA256(SHA256(digest))`, then commits that value in a real OP_RETURN transaction, double-hashes the transaction, and follows its merkle path to a pinned block. Its first double-hash output is a commitment hash, not the anchor transaction id. G20 rejects it when the bundle contains the actual txid; it accepts the wrong coherence handle when the bundle instead contains the earlier commitment hash. The existence/time commitment remains valid; this is not a forged timestamp or C1/C2 attack. It is a counterexample to the registered handle's stated transaction identity.

**Exact proposed fix:** replace the heuristic with a declared transaction witness: transport the exact transaction-id preimage and an explicit path position; parse/consume it under a pinned Bitcoin transaction grammar; verify its relationship to the preceding OTS commitment, compute its txid, and verify the remaining declared transaction-to-block merkle path. Specify non-witness serialization if SegWit is allowed. Alternatively make the current calendar shape a visible supported-proof subset and require that the first pair's input is an actual conforming transaction preimage containing the path commitment. Merely finding two adjacent hash operations is insufficient. Making txid purely advisory requires a registered correction/amendment if its identity/coherence role is retained in the governing requirements.

The closed operation/tag set is a new scope restriction, not solely CLARIFY. SHA-1 commitments are weaker, but rejecting arbitrary unknown attestations or strong unused operations is not an A9 protection theorem. Fix exact OTS version/source digest, LEB128 bounds and redundant-form policy, duplicate-branch rules and total resource bounds; library “0.4.x” is not an immutable dependency. The local 0.4.5 decoder accepts redundant LEB128 groups, so a shortest-form assumption would diverge. No P8 layout change is necessary for unsigned transaction evidence; new evidence conformance vectors are necessary.

### F10 — Medium: G21 contradicts the registered hybrid branch

**Location:** draft G21 lines 167–178; A9.6; E §5.2.

After allowing an ML-DSA-65 SPKI for kms, G21 says “Each must parse as P-256: algorithm 19 …”. A literal implementer rejects every hybrid kms key. Another applies the implied exception. A9 authorizes the hybrid; both readings cannot govern.

**Exact proposed fix:** “gpg must parse as the specified v4 P-256 public-key body. kms must parse as P-256 DER SPKI under the fallback, or as the exact ML-DSA-65 SPKI specified by the dated branch supplement under the hybrid. The rule is selected by the installed governing spec and slot, never by key bytes alone.” No extra amendment is needed for A9's already authorized supplement. Hybrid signed encodings/vectors are already an A9 obligation; the blanket no-vector-change claim must explicitly exclude them.

### F11 — Medium: G14/G17/G33 conflict, and several “closed schemas” remain sketches

**Location:** draft G17/G14, G08/G09/G22, G15, G33.

G17 makes “any other schema failure” INVALID, while G14 makes an absent required member UNVERIFIABLE. G33 adds a mandatory issuer_record and calls it never verdict-affecting; removing it now changes VALID_STRICT to UNVERIFIABLE, and giving its fields bad types gives INVALID. That is a new completeness rule even if the observations' values do not influence time policy.

Decimal strings have no canonical grammar/range: headers can contain both `"1"` and `"01"`, creating a normalization/duplicate-height fork. Repository entries are `[…]`, not a fully specified schema; key-to-D pairing, time field types and interval constraints must be concrete. Genesis previous_sha256, version ordering, profile value, root provenance/publication/revocation types, and dependency-manifest top-level structure remain unspecified. A matching frozen hash can make dependency bytes unique at runtime, but it does not tell the freeze author what object to construct.

**Exact proposed fix:** supply machine-checkable tables for every field with JSON type, cardinality, byte encoding, bounds and cross-field invariants. Height grammar is `0|[1-9][0-9]*` with an explicit maximum; no aliasing by leading zeros. State G14's absence exception before G17's generic schema rule, including nested evidence members. Special-case git.object_format exactly as A9.5 requires: absent and unsupported values are UNVERIFIABLE with A9's codes, not generic schema INVALID. For issuer_record choose either optional unsigned diagnostics or mandatory issuance metadata; if mandatory, say “presence and schema affect the verdict; its reported values do not alter verification parameters.” Define its duration grammar and policy-version syntax. No new signed receipt member is needed.

### F12 — Medium: G09's update rule preserves one horizon but does not freeze all acceptance inputs

**Location:** draft G08/G09/G22; A9.4/A9.5.

The close-only inequality correctly preserves eligibility previously granted through as_of **if** starts, keys, D, L and prior entries are immutable and as_of is nondecreasing. The draft explicitly freezes finalized ends but does not fully state these other invariants. Changing a KSK's L from 21 days to one day after its end is closed removes a formerly usable witness without deleting the key or changing the endpoint. The release checker is therefore underspecified. Open KSKs also use [start, as_of] rather than [start, as_of+L]; that is a reasonable finite coverage convention but must be expressed as reliance policy rather than silently inferred.

**Exact proposed fix:** immutable identity, key bytes, D, signing_start and L for every existing entry; nondecreasing as_of; increasing authenticated versions; immutable finalized ends; transitions null→end only with resulting reliance end >= previous as_of; unique canonical pins, immutable existing hashes; previous_sha256 exactly binds the prior approved config. Define finite reliance of an open KSK as [start, as_of] explicitly. Archive the actual config hash as a declared verification input.

Appending pins can make an earlier attestation in the same proof qualify under G05 and thus change T or even VALID_STRICT to INVALID. Example: initially only h2 qualifies, inside c1; later coverage of h1 < h2 selects T1 before declared−ε. This does not violate A9's exact-output contract for identical declared inputs, because the config changed. It does refute any stronger claim that append-only updates preserve all verdicts merely by preserving witnesses. State this distinction explicitly; do not replace A9's contract with a monotonic-verdict promise. No new NARROW-MODEL is needed for an accurately limited coverage convention. Retired-KSK manufacture during the already adopted L extension is A9's acknowledged residual; an inadvertently longer horizon is a release failure, not permission to claim the exposure is bounded by the real retirement date.

### F13 — Medium: G22 does not yet provide reconstructible trust anchors

**Location:** draft §C/G22, lines 388–414; P §5; RFC 9718.

RFC 9718's publickeyinfo is optional, so an XML archive can contain a DS digest without the public-key bytes needed to reconstruct DNSKEY RDATA. The draft's source procedure assumes those fields exist. It also supplies no concrete signing_start values, as GAPS requested. Byte equality excludes a REVOKE-bit form; it does **not** reject an archived old flags=257 RR solely because evaluation occurs after revocation. A9 uses reliance, not revocation, to decide that time question. [RFC 9718 §2.2](https://www.rfc-editor.org/rfc/rfc9718.html#section-2.2).

**Exact proposed fix:** require an archived authenticated source containing each full public key, or obtain it from an archived root DNSKEY RRset and cross-check the DS digest against independently authenticated IANA material. Record exact RDATA and complete interval starts/ends/L in the actual pre-freeze config, with source digests and the trusted ICANN CA/bootstrap procedure for .p7s verification. Keep publication/revocation informational as A9 requires. Replace “after 2027-01-11” with “when the presented RDATA has REVOKE set”; the period gate supplies temporal exclusion. No additional receipt bytes or P8 vectors need change.

## Change-accounting verdict

Do not approve §K's blanket “none” as written. The file's draft status is not an exemption from A9: A9 incorporates an ENCODING-V1 signing baseline and registers C4/C5/C6 meanings and the object_format outcomes. A later unregistered profile cannot override those by relabeling a change as wording.

The owner can make many new completion choices without an amendment: a concrete container, an independent trust-config mechanism, explicit key transport, exact DNSSEC algorithms, a body encoding, and a frozen catalog. These are **new owner choices**, not automatically existing-rule CLARIFYs. Restrictions on wildcards, OTS operations/attestations, signature subpackets, canonical transport, git headers and repository algorithms should be visible as supported-path limits. None by itself demonstrates that protection available within A9's model has been conceded.

There is no established unavoidable NARROW-MODEL finding. There are two conditional author surfaces: excluding a channel-capture path because config authorization is shared (F04), and weakening an actual pre-issue commitment claim to a numeric chain-time comparison (F01). Implement the missing authorization boundary or correct the claim explicitly; do not announce that either issue has already disappeared. G05 requires a registered reading, not an invented cryptographic security claim about all-branch coverage.

“No signed byte changes” is only defensible as **no mandatory attestation-frame layout change for these resolutions**. Freezing edited spec/vector objects changes their signed hashes; converting the DNS body changes its anchored S preimage and needs a fresh stamp; trust configuration gets a new detached signature; signature policies can change allowed signed signature output. Existing archived proof bytes cannot be converted in place while retaining their stamp. The authorized hybrid supplement still changes slot encoding and requires its own vectors. Existing fallback P8 golden/rejection expectations need not be rewritten merely to add above-codec policies, but boundary and full-profile vectors remain necessary.
