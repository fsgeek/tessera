# V1 spec-sufficiency probe — 2026-10-13

The four documents do **not yet determine an interoperable offline V1 verifier**.
The first end-to-end stopping point is the explicitly OPEN bundle container; the
next independent stop is the explicitly OPEN DNSSEC snapshot body. Beyond those
formats, required binding forms, temporal witness selection and confirmation
rules, and the git assertion's relation to the receipt still permit materially
different acceptance policies. The byte codec is substantially more specified
than the evidence/verdict layer.

This is a bounded independent-implementer experiment, not a C-row discharge,
registered conformance run, gate ruling, or finding that an existing verifier
accepts an attack. **No actual receipt was shown to receive divergent verdicts.**
Rows marked yes identify a plausible verdict fork under unresolved rules; the
acceptance-sensitive rows give concrete distinguishing input conditions.

## Design and stopping result

The throwaway [probe](indep-verifier/verifier.py) takes **raw `A_sig` and raw
`F_manifest` files**, not an invented bundle format. It implements framing,
number-free canonical payloads, schemas, structural signature checks and receipt
consistency. It also exposes the snapshot envelope and isolated issuance-window
comparison. See [README](indep-verifier/README.md) for implemented checks and limits.

No execution returns `VALID_STRICT`. All outputs have `v1_verdict: null`; a
structurally passing receipt stops before signatures, authority and time. No
untrusted input time, fingerprint, pin or claimed validation result substitutes
for verified evidence. The local `probe_status` and `probe_reason` fields are
deliberately not the frozen V1 report schema.

The table records every design-level choice or stop encountered, including
unimplemented stages reached by design inspection. It does not enumerate routine
Python choices that cannot change protocol acceptance. **VERDICT-AFFECTING yes**
means a different reasonable reading/completion can change VALID_STRICT / INVALID
/ UNVERIFIABLE or prevent reaching a verdict; a reason-code-only difference is no.
“Could accept” means after all other checks pass, not that this probe accepts it.

## Verification evidence and limits

The local probes were written from these documents and constructed synthetic
objects. They use no project vectors or existing signatures. Synthetic rule-O
MPIs establish syntax only, not ECDSA validity; unknown-algorithm opaque strings
establish only the allowed codec route. Changed syntactically admissible signature
bytes change the anchor digest; this is not a demonstrated OTS verification.

Command:

```sh
PYTHONDONTWRITEBYTECODE=1 python3 docs/reviews/spec-sufficiency/indep-verifier/selftest.py
```

Final local run: **9/9 tests passed**, Python syntax parsed successfully, and a CLI run on a synthetic structurally passing classical receipt returned **STOPPED / FULL_VERIFIER_SPEC_GAPS**, `v1_verdict: null`, `T: null`. Runtime: Python 3.14.6, Unicode 16.0.0. No dependencies were installed. These results validate only the implemented probe subset.

The probe deliberately stops
before full verification. The most useful next spec work is to fix G01–G07 and
the container/snapshot/trust formats; completing this throwaway code by selecting
those rules would conceal the result the experiment is meant to reveal.
