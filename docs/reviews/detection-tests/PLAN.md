## 1. Failure-Model Context (`docs/V1-CONTRACT.md` §§2–4, `docs/V1-DETECTION-CONTRACT.md`)

Under `V1-CONTRACT.md` §§2–4:
- An attacker who alters a receipt or moves its signatures is rejected cryptographically by the relying-party verifier (G1, G3, G10).
- An attacker who signs with unauthorized keys is rejected by G4 **only while the DNS and git authority records are not captured**.
- **If an attacker captures both DNS and git authority records**, honest receipts remain protected under G10's stated evidence conditions (service keys stay secret and unmisused, independent release boundary holds), **but newly issued receipts under attacker-selected keys pass verification and capture need not be visible** (`V1-CONTRACT.md:37, 52-53, 71-72`; the service-key listing was cut).
- **An attacker who captures the issuing AWS account is NOT protected by cryptography** — it can issue receipts that verify cleanly (`V1-CONTRACT.md:73`).
- **Requester authorization is NOT settled by receipt verification or by `D6c`:** `V1-CONTRACT.md` §3 explicitly excludes "who submitted the bytes," and `V1-DETECTION-CONTRACT.md:132-134` states that "a requester inside the issuing account" is **not covered**. A principal able to submit work through the authorized issuer/signer path (for example causing the signer role to invoke `kms:Sign`) can obtain a signature without directly holding `kms:Sign`, and `D6c` will not fire for it.
- Detections D1–D10 therefore form the operational early-warning and accounting layer around the issuing account and service surface:
  - **D1–D4** guard the public API perimeter (throttling/flood, key probing, malformed/oversized abuse, unexpected key volume or uninvited keys).
  - **D5–D6 & D8** guard signing integrity and receipt integrity inside the account (unexpected signer refusals, unaccounted `kms:Sign` / `useToSign` or foreign-principal `kms:Sign`, corrupted or mismatched receipts).
  - **D7 & D9** make tampering with the control plane or silencing the watcher noisy, though as the detection contract states, neither defeats a careful administrator-level attacker in the same account.
  - **D10** catches operational faults and runaway spend.

Passing only a subset of rows **never** closes the entire detection gate; every `NOT COVERED`, `DID NOT FIRE`, or `OPEN` row leaves that part of the gate explicitly open.

## 2. Observation Endpoints, Latency Standards, and Correlation Protocol

### Two observation endpoints (recorded separately) plus alarm state
1. **CloudWatch Alarm State (metric/alarm detections: D1–D4, D9, D10):** `StateUpdatedTimestamp` from `cloudwatch:DescribeAlarmHistory` when the alarm transitions `OK -> ALARM`, following a verified `OK` baseline (`DescribeAlarms`).
2. **SNS Delivery (`sns` endpoint): NOT COVERED (removed, steward pass 2026-11-23).** Observing SNS delivery required subscribing a test queue to the production topic `tessera-v1-alarms` and later unsubscribing it; Codex found that a lost `Subscribe` reply or a failed unsubscribe could leave a production subscription behind and that recovery could remove a subscription this run did not create (`CODEX-CONFIRM.md` finding 2 and the second additional HIGH). The suite no longer calls the production topic or any of its subscriptions, so no row records an SNS-endpoint observation. SNS-to-email delivery is inferred only from the email arrival below.
3. **Email Arrival (`email` endpoint):** Arrival timestamp in the author's mailbox, read read-only by the steward after each test and joined back using the runner's `steward_mailbox_handoff` identifiers (`row_id`, `event_time_utc`, `deadline_utc`, CloudTrail `eventID`, alarm name + `StateUpdatedTimestamp`, resource name). Establishes the contract's real-time notification promise ("the author's email is the only real-time path").

### Latency standards (named explicitly per row)
- **Original Detections table standard:** `event-to-email` (time from triggering event to arrival in the author's mailbox: 10 min for D1–D2 and regional D7; 15 min for D3–D4; 20 min for D5/D8; 1 h for D6, watcher IAM D7, D10).
- **D1–D4 as-built standard:** `event-to-alarm-state` (one evaluation period — 5 min for D1/D2/D3c/D4b/D4c, 1 h for D3a/D3b, 1 day for D4a/D4a-other — plus CloudWatch's evaluation delay), while `event-to-email` remains measured against the original contract table's latency column (10 min for D1–D2; 15 min for D3–D4).
- **Trigger timestamp for threshold rows:** UTC timestamp of the N-th qualifying request that crosses the threshold (50th 403 for D1c/D2a/D2b; 5th 400 for D3a; 51st logged daily request for D4a; 1st `QUOTA_EXCEEDED` for D4c).
- **SNS endpoint:** Not measured (removed; see §2).

### Correlation by identifiers (never subject + time alone)
- **D1–D4:** Verified `OK` pre-stimulus alarm state, per-attempt client UUIDs and `x-amzn-requestid`s, read-only CloudWatch Logs correlation against `/aws/apigateway/tessera-v1-issuer-access` (proving exact logged `status`, `error`, `apiKeyId`), CloudWatch `AlarmName` + `StateUpdatedTimestamp` (read-only `DescribeAlarmHistory`), and steward email arrival.
- **D7 (EventBridge):** Paginated read-only `cloudtrail:LookupEvents` parsing `CloudTrailEvent` JSON to match exact `eventName`, UTC window, target resource ID/ARN, and `errorCode == None` (proving the tamper action succeeded, never crediting setup/cleanup/AccessDenied alerts), joined by exact CloudTrail `eventID` UUID against the steward email.
- **D7 IAM (watcher):** Not executed; all IAM mutations removed (steward pass 2026-11-23).

### Evidence classes (never merged)
- **PRODUCTION PATH:** Triggering event occurred on the production resource or production request path within Hard Safety Rules 1–4 (r5).
- **EQUIVALENT BY SCOPE:** Fired on a throwaway `tessera-dtest-<run>-*` resource in `us-east-2`, **and** post-writing inspection of the deployed rule and every downstream stage (input transformer, watcher filters, permissions) confirms nothing filters by resource or behaves differently for the production resource, **and** live firing + delivery is observed. Prior to live firing, throwaway rows are **`EQUIVALENT BY SCOPE (CANDIDATE)`** only.
- **NOT COVERED:** Cannot be tested within Hard Safety Rules 1–4 (r5), not yet built/deployed, or rule filters specifically to a production resource.

## 3. API Quota, Rate, and Isolation Plan (D1–D4)

Hard Safety Rules 3 (r5) and 4 constrain all live API Gateway tests:
- **No recorded POSTs (r5 Rule 3):** `D3b` (oversized 413 `POST`) writes a durable `REFUSED/TOO_LARGE` record and tombstone (`service/issuer/tessera_issue/api.py:134-149`), and the watcher locks a 400-day trace for it. **`D3b` is removed and marked NOT COVERED.** Only `D3a` (missing/non-UUID `Tessera-Request-Key`, rejected 400 at `api.py:118-120` before any DynamoDB read or write) is permitted.
- Usage plan rate limit: **5 rps, burst 20**. Tests enforce ONE process-wide client-side `RateLimiter` (default **≤ 2 rps**, burst **1**, no redirects, no retries).
- `smoke-test` daily quota: **100 requests/day**; `smoke-test` D4 volume alarm: **50 logged requests/day**. Runner checks today's prior `smoke-test` access-log count before starting smoke-key rows.
- D1c 4XX backstop alarm: **50+ 4XX responses in 5 minutes**.
- **Clean baseline condition:** Before every API row, the runner verifies target alarms are in `OK` state via `cloudwatch:DescribeAlarms` (any reset duration such as 10–15 min is a test-design estimate, not the trigger condition).
