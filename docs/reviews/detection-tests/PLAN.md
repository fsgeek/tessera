## 1. Failure-Model Context (`docs/V1-CONTRACT.md` §4)

Under `V1-CONTRACT.md` §4:
- An attacker who alters a receipt, moves signatures, or signs with unauthorized keys is defeated cryptographically by the relying-party verifier (G1, G3, G4, G10).
- **An attacker who captures the issuing AWS account is NOT protected by cryptography** — it can issue receipts that verify cleanly.
- Detections D1–D10 therefore form the operational early-warning and accounting layer around the issuing account and service surface:
  - **D1–D4** guard the public API perimeter (throttling/flood, key probing, malformed/oversized abuse, unexpected key volume or uninvited keys).
  - **D5–D6 & D8** guard signing integrity and receipt integrity inside the account (unexpected signer refusals, unauthorized or unaccounted `kms:Sign` / `useToSign`, corrupted or mismatched receipts).
  - **D7 & D9** make tampering with the control plane or silencing the watcher noisy, though as the detection contract states, neither defeats a careful administrator-level attacker in the same account.
  - **D10** catches operational faults and runaway spend.

Passing only a subset of rows **never** closes the entire detection gate; every `NOT COVERED` or `DID NOT FIRE` row leaves that part of the gate explicitly open.

## 2. Observation Endpoints, Latency Standards, and Correlation Protocol

### Two observation endpoints (recorded separately) plus alarm state
1. **CloudWatch Alarm State (metric/alarm detections: D1–D4, D9, D10):** `StateUpdatedTimestamp` from `cloudwatch:DescribeAlarmHistory` when the alarm transitions `OK -> ALARM`.
2. **SNS Delivery (`sns` endpoint):** A throwaway SQS queue (`tessera-dtest-<run>-obs-q`, SSE-SQS, queue policy granting `sns.amazonaws.com` `sqs:SendMessage` conditioned on `tessera-v1-alarms` ARN) temporarily subscribed to `tessera-v1-alarms` under Hard Safety Rule 1's narrow exception, and unsubscribed and deleted during cleanup. **The topic policy and existing subscriptions are never modified**; if `sns:Subscribe` fails for policy/permission reasons, the runner stops immediately and reports it. Records SNS `Timestamp` (from the SNS envelope) and SQS `SentTimestamp` / receive time. Establishes delivery through SNS only.
3. **Email Arrival (`email` endpoint):** Arrival timestamp in the author's mailbox, read read-only by the steward after each test and provided back with subject, event time, and correlating identifiers. Establishes the contract's real-time notification promise ("the author's email is the only real-time path").

### Latency standards (named explicitly per row)
- **Original Detections table standard:** `event-to-email` (time from triggering event to arrival in the author's mailbox).
- **D1–D4 as-built standard:** `event-to-alarm-state` (one evaluation period plus CloudWatch's evaluation delay) for the alarm-state endpoint, while `event-to-email` remains what item-3 tests measure against the original table's latency column (10 min for D1–D2; 15 min for D3–D4).
- **SNS endpoint:** Intermediate latency (`event-to-SNS-receipt`), recorded separately and never substituted for email arrival.

### Correlation by identifiers (never subject + time alone)
- **D1–D4:** CloudWatch alarm name, `StateUpdatedTimestamp`, API Gateway request IDs (`x-amzn-requestid`) / client correlation UUIDs logged in the test ledger, exact trigger window UTC start/end, and matching SNS `MessageId` / email body alarm name + `StateChangeTime`.
- **D7 (EventBridge):** CloudTrail `eventID` (from `cloudtrail:LookupEvents` and present in EventBridge/SNS/email body), exact throwaway resource name/ARN (`tessera-dtest-<run>-*`), and event `eventTime`.
- **D7 IAM (watcher):** CloudTrail `eventID`, throwaway IAM resource name (`tessera-dtest-<run>-*`), and watcher finding ID / `eventTime` in the SNS/email message body.

### Evidence classes (never merged)
- **PRODUCTION PATH:** Triggering event occurred on the production resource or production request path within Hard Safety Rules 1–4.
- **EQUIVALENT BY SCOPE:** Fired on a throwaway `tessera-dtest-<run>-*` resource in `us-east-2`, **and** post-writing inspection of the deployed rule and every downstream stage (input transformer, watcher filters, permissions) confirms nothing filters by resource or behaves differently for the production resource.
- **NOT COVERED:** Cannot be tested within Hard Safety Rules 1–4, not yet built/deployed, or rule filters specifically to a production resource.

## 3. API Quota, Rate, and Isolation Plan (D1–D4)

Hard Safety Rules 3 and 4 constrain all live API Gateway tests:
- Usage plan rate limit: **5 rps, burst 20**. Tests enforce a conservative client-side rate limiter (default **≤ 2 rps**, no burst > 1).
- `smoke-test` daily quota: **100 requests/day**; `smoke-test` D4 volume alarm: **50 requests/day**.
- D1c 4XX backstop alarm: **50+ 4XX responses in 5 minutes**.

Planned request budget and pacing so tests do not cross-contaminate:

### Test-code limitations / mismatches discovered during scope review (tests left unmodified)

Per the brief, test code in `service/detect/tests-live/` was **not** altered after reading the implementation. Record these four findings before execution:

1. **EventBridge D7 SNS payload format vs. `observer.py:parse_sns_sqs_message`:** `main.tf:91, 118` transforms EventBridge D7 events into a plain-text sentence (`"Tessera D7 (control-plane change): <name> on <src> by <who> at <at>; error <err>; CloudTrail event <id>..."`) rather than raw CloudTrail JSON. `parse_sns_sqs_message` only parses JSON dicts for `identifiers`, so for EventBridge D7 messages `identifiers` will be `{}` while the full text (including `CloudTrail event <id>`) is preserved verbatim in `raw_message_excerpt`. No data is lost, but `eventID` extraction from `raw_message_excerpt` during results compilation will need a simple regex/manual read rather than relying on `identifiers["cloudtrail_event_id"]`. (Watcher JSON findings and CloudWatch Alarm JSON payloads ARE parsed into `identifiers`.)
2. **Resource name absent from D7 notifications — CloudTrail `LookupEvents` needed for correlation:** Neither the EventBridge D7 `input_template` (`main.tf:91`) nor the Watcher IAM finding (`cloudtrail.py:137-138`) includes the target throwaway resource name (`tessera-dtest-<run>-*`); both include the CloudTrail `eventID`. `run_tests.py` records each test's UTC window and throwaway resource name, and `observer.py` includes `lookup_cloudtrail_event_id(...)`, but `run_tests.py` does not automatically call `lookup_cloudtrail_event_id` after each D7 test. During the live run, run a read-only `cloudtrail:LookupEvents` pass (after ~5 min indexing lag) to map each notification's `eventID` to its exact `tessera-dtest-<run>-*` resource name.
3. **`D3a` / `D3b` 1-hour alarm reset (`access.tf:86, 91`):** `tessera-v1-d3-smoke-test` has `period = 3600` (1 h) and no `ok_actions`. After `D3a` transitions the alarm to `ALARM`, `D3b` must wait **> 65 minutes** (until the 6 × 400 datapoints leave the 1 h window and `DescribeAlarms` shows `OK`) before running, otherwise `D3b` will not produce a fresh `OK -> ALARM` notification.
4. **Cross-triggering of D7 IAM during `d7-lambda` and `d7-sup-sqs` during observer setup:**
   - `run_d7_lambda` creates and deletes throwaway role `tessera-dtest-<run>-fn-role`, which will also emit `iam:CreateRole`/`DeleteRole` D7 IAM findings from the watcher ~25–60 min later.
   - `AlarmObserver` itself calls `sqs:SetQueueAttributes` and `sqs:DeleteQueue` on `tessera-dtest-<run>-obs-q`, which will also emit D7 SQS notifications in addition to `run_d7_sup_sqs`.
