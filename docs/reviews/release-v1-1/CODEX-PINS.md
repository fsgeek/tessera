# Candidate 4 pins review

- **MEDIUM — A failed update can publish half the output.** The command replaces `trust.json` before opening the constants staging file. If a stale `release_constants.py.new` already exists, the exclusive open fails after the new trust is live. The old constants then bind the old trust hash, and a retry hits the same obstruction. A write error can also leave an incomplete staging file. The test covers only a successful rewrite. Stage both outputs before replacing either, clean up this invocation’s staging files on failure, and restore the original trust if the constants replacement fails. Individual renames still leave an interruption window between the two replacements. `service/verifier/release/release_tool.py:507–516,764–766`, `service/verifier/tests/test_release_tool.py:304–318`.

- **MEDIUM — Overlapping invocations can drop pins and move the horizon backward.** Two runs can read the same base. A slow run can finish its explorer calls after a fast run has published a different set of pins and a later `as_of`. The slow run then replaces the new trust with its stale-base result, losing the fast run’s additions and potentially lowering `as_of`. The exclusive staging open protects only while that staging path exists. Serialize the read-through-publish operation for each trust file, or hold a publication lock while checking that the on-disk trust still matches the bytes read at the start and refuse a stale result. `service/verifier/release/release_tool.py:490–502,507–516`, `docs/V1-PROFILE.md:602–607`.

- **LOW — Canonical JSON alone does not establish a valid base.** With an already invalid draft containing a height key such as `0976209`, the byte round-trip can pass and the command can add `976209`, leaving two spellings of the same height. A profile-valid input excludes that scenario. For a single invocation on such an input, exact-height conflicts refuse, all existing pins and other members are preserved, and the resulting `as_of` stays at or above the valid input horizon. `service/verifier/release/release_tool.py:485–504`, `docs/V1-PROFILE.md:1213,1505–1506,1685–1707`.

The actual maximum includes only headers fetched in this invocation and the previous horizon. The profile requires a valid nondecreasing UTC horizon and uses it to cap reliance on open entries. It prescribes no header-time formula. Label the rule as the steward’s preparation policy for owner approval, or cite the owner’s decision if recorded. The local-clock check is also preparation policy. `service/verifier/release/release_tool.py:23–28,453–454,490–502`, `docs/V1-PROFILE.md:597–607,1687–1705`.
