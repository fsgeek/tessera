# Scoped review: gpgv-free signing session and the pins fix (Codex, 2026-11-28)

Brief: BRIEF-gpgv-and-pins-fix.md, material inline (the first run on 2026-11-27 never read a file: bwrap could not create its network namespace; the steward did not notice for a day).

- **MEDIUM — The pins command can still leave mismatched outputs live.** `service/verifier/release/release_tool.py:541–552` stages both outputs before replacing either, which closes the stale `.new` failure. If the process is killed after replacing `trust.json` at line 542, the old constants remain live. A recoverable error can produce the same result if the constants replacement fails and the filesystem then refuses creation of the rollback temp file. The rollback test injects only the second rename failure and lets rollback succeed.
- **MEDIUM — A symlink alias bypasses the pins lock and can leave the canonical pair mismatched.** `service/verifier/release/release_tool.py:515–516,529–545` locks by the supplied absolute pathname, follows symlinks when reading, and replaces the supplied directory entry when writing. Run `pins trust.json` and `pins alias.json` in the same directory, with `alias.json` initially a symlink to `trust.json`. Both can read and recheck the same base under different locks. If the canonical run publishes first and the alias run publishes second, the alias becomes a separate file and the shared `release_constants.py` binds the alias run’s trust bytes. The canonical trust and constants now disagree. Same-path invocations are serialized.
- **MEDIUM — The NUC check does not establish that the invoked `gpgv` is the build that passed the vectors.** `docs/V1-RELEASE-PROCEDURE.md:74–78,141–143` and `docs/ceremony/release-v1-1-SHEET.md:226–229` rely on the NUC’s earlier 9/9 result. If the NUC updates `gpgv` or a different executable takes precedence on `PATH` before publication, the genuine signature can still pass and the one-byte mutation can still fail. Those two results do not establish that the replacement build reproduces upstream on all nine vectors, as R3 requires.
- **LOW — The signing receipt overstates what the offline check establishes.** `docs/ceremony/sign-release.sh:113–117` prints `RULE O PASS, signed by` after checking packet syntax and the claimed issuer. A signature with the expected issuer and an in-range but incorrect ECDSA value can pass that check and leave on OUT. The offline check still meets R3’s rule-O requirement, and the documented NUC gate would refuse publication of that signature. The stated cost of discovering that failure after shutdown is real.
- **LOW — Both script references point to the wrong procedure step.** `docs/ceremony/sign-release.sh:12,113` sends the owner to step 14, which is the offline rule-O check already completed. The owner following that reference needs step 16 for NUC verification and the changed-byte refusal.
