# Verifier release 1 candidate review

## HIGH

**H1 — Candidate preparation can determine what the author signs.**
`docs/V1-RELEASE-PROCEDURE.md:49–56,83–94,127–131`, `docs/ceremony/release-v1-1-SHEET.md:17–22,55–79,119–126`, `service/verifier/release/release_tool.py:225–252`. A10.4.2 requires comparison with an approved baseline kept outside the operational environment (`docs/phase-0-prereg-amendment-10.md:628–633`). The frozen catalog fixes the specification and policy parameters. The freeze explicitly leaves verifier code and inventory to each release (`docs/V1-PROFILE.md:1889–1893`). The NUC prepares the candidate and supplies its source commit and comparison hashes. The checker compares archive parts against that same candidate commit. Separate hardware and a local rebuild establish byte agreement with the proposal. For example, a compromised candidate preparer could propose changed verifier logic or a changed repository authorization interval while retaining the expected displayed fingerprint, catalog, and public pin values. If the author follows the sheet, the printed hashes and prescribed checks can all agree and the author can authorize the unwanted bytes with the genuine card. This does not require a hash collision, key extraction, or a change to the offline signing script. The author needs an independently approved source and trust baseline, or an explicit review of the changes against one, before approving the exact archive hash. This HIGH touches what gets signed and is the one for scoped confirmation under the brief.

**H2 — Acquisition can unpack bytes other than those authenticated by R3.**
`service/verifier/release/release_tool.py:376–394`, `docs/V1-PROFILE.md:1906–1909,1943–1948`. The checker reads the signature for rule O, gpgv reopens the signature and archive paths, and acquisition reopens the archive after gpgv returns. If a download or synchronization process replaces the archive in that interval, acquisition consumes the replacement. R2 is a consistency check, so a replacement with changed code or trust and matching internal hashes can still unpack. The production catalog pin would still reject a changed catalog under the genuine checker. The publication claim at `docs/V1-RELEASE-PROCEDURE.md:105–108` inherits the same byte-binding gap. Check and consume private snapshots of the archive and signature. This concerns acquisition after signing.

## MEDIUM

**M1 — The rehearsal can pass without exercising the registered production refusal paths.**
`docs/ceremony/sign-release.sh:96–116`, `docs/ceremony/release-REHEARSAL-SHEET.md:120–123`, `docs/releases/v1-1/SUMMARY.md:91–111`. Frozen R4 requires refusal at acquisition with the TEST key offered and refusal by the installed production verifier through §3.5 (`docs/V1-PROFILE.md:1980–1982`, `docs/phase-0-prereg-amendment-10.md:650–657,772`). The sheet invokes only `verify-sig` for the two key offerings. With the production fingerprint fixed, a genuine TEST signature is refused even when its public key is offered. The script calls that result a row 36 pass on any nonzero exit, including a checker I/O error, and uses the same permissive expectation for the changed-byte check. A regression in `acquire` or in installed TEST-override handling can therefore coexist with the sheet's PASS. Make the acquisition checks require the expected refusal and no unpacking. Include the installed-verifier leg in the recorded rehearsal with the expected `TEST_AUTHORITY_REFUSED`, exit 2, and no verdict, on a setup capable of running the installed verifier. The NUC transcript is existing evidence for that leg. Describe explicit verification of the intentionally cross-signed negative fixture as a control, since it is not an R4(a) TEST release (`docs/V1-PROFILE.md:1963–1982`, `docs/releases/v1-1/SUMMARY.md:97–98`).

**M2 — Install checks a manifest-selected subset and assumes the installer tree is already authenticated.**
`service/verifier/release/release_tool.py:156–187,407–416`, `service/verifier/install.sh:20–39`, `docs/V1-PROFILE.md:1906–1909,1919–1927`. A listed file changed after acquisition fails against an intact manifest. An extra file in the unpacked source tree is never enumerated by `bindings`, and the installer adds provisioned constants and installs the tree editable. In a previously used or copied tree, a stray package module can be visible to the installed verifier while the manifest-selected files all match. A coherently changed trust file, constants and manifest also pass if the installer is started on that tree without authenticated acquisition. A consistently changed production catalog still fails the authentic checker's frozen constant. State the required fresh authenticated tree and check its actual pre-install inventory, accounting explicitly for installer-generated files. The release mode is no independent signature check.

**M3 — Acquisition has no expected namespace and only partially checks the release envelope.**
`service/verifier/release/release_tool.py:156–187,390–395,428–433`, `docs/V1-PROFILE.md:1895–1909,1913–1927,1963–1978`. When both the supplied fingerprint and key are TEST, acquisition can unpack a `PRODUCTION`-labelled archive under that TEST signature. That is absent or substituted bootstrap authority, not a bypass when the caller supplies the genuine production fingerprint. The same interface also has no explicit TEST namespace selection. Separately, a signed archive can omit required parts such as the lock or relying-party text, or carry an internally consistent numeric trust version, and still print `ACQUIRED`. Require the selected namespace, the required part classes and the closed manifest's string types, and retain authenticated key selection as a prerequisite. The intentionally mismatched row 36 fixture is for refusal testing.

**M4 — R3 does not establish the checker and gpgv identity described in the summary.**
`docs/releases/v1-1/SUMMARY.md:38–40,135–136`, `service/verifier/release/release_tool.py:364–386,428–431`, `docs/V1-PROFILE.md:1103–1109,1944–1956`. Fetching a separate checker from the same GitHub source gives availability before acquisition. A compromised distribution source can still supply a different checker. Also, ordinary acquisition uses the binary named by PATH or the override without evidence it is the pinned build or an eligible distribution build. The sheets compare version lines, which can match across different builds. Record how the checker is authenticated and which gpgv build passed the vectors. The checker also rejects an otherwise rule-O-conforming signature from the authenticated sole key when it lacks the optional hashed issuer fingerprint. That is an extra acceptance restriction, not the frozen grammar. Prevalidate the expected primary key and use verification with that sole key to establish signer identity under R3.

**M5 — The media instructions omit checks the custody procedure relies on.**
`docs/ceremony/release-REHEARSAL-SHEET.md:7–10,79–100,127–131`, `docs/ceremony/release-v1-1-SHEET.md:7–12,81–99`, `docs/ceremony/sign-release.sh:19–42,114–116`, `docs/V1-RELEASE-KEY-CUSTODY-DRAFT.md:119–148`. INPUT intentionally crosses from a networked review boot to the offline boot. A FAT label does not identify the physical stick or certify its history. The rehearsal OUT row does not say it must be never-NUC on entry. The sheets omit the prior ceremony's internal-disk mount check (`docs/ceremony/CEREMONY.md:92`). Additionally, rehearsal transfers and executes the vector runner from INPUT and checks neither it nor its fixtures offline. A mix-up can bring a previously networked everyday stick into the offline session. A modified runner or fixture set can also report `9/9 match` and leave apparent qualification evidence for the production signing tools. Identify both physical sticks before formatting and mounting, make the boot and disk checks explicit, and compare the rehearsal vector inputs with a separately recorded digest before execution. The draft's candidate-content and media rules need an explicit disposition for the transferred scripts. The final custody procedure must also say how every backup stays outside the operational environment, as A10.4.2 requires. The production sheet's instruction to put the card back apart from its backup does not supply that record (`docs/ceremony/release-v1-1-SHEET.md:136–138`, `docs/V1-RELEASE-PROCEDURE.md:114–121,151–154`). The rehearsal's INPUT reuse itself is role-preserving if it is kept out of the NUC and other everyday computers.

**M6 — The sheets have ambiguous stop conditions and a definite output-count error.**
`docs/ceremony/release-REHEARSAL-SHEET.md:55–77,102–123`, `docs/ceremony/release-v1-1-SHEET.md:51–79,101–131`, `service/verifier/release/release_tool.py:255–275`, `docs/ceremony/sign-release.sh:65–78,119–129`. A successful source run prints 14 data lines **plus** the PASS line. The freeze-object wants give only hash prefixes, and neither sheet makes the paper/ORCID discrepancy an explicit stop at the point it is recorded. Use full expected freeze digests and specify a stop for missing or unequal values. The production sheet also needs an explicit Ctrl-C and remove-the-card instruction for an unexpected card line. The script retries card discovery but does not enforce the printed serial or independently establish Tails pinentry and touch behavior. For OUT, a failed write can leave a signature on the stick after `cp` has written the first file, and failed `sync` or failed listing/hashing can still be followed by PASS. Treat all failed or interrupted runs as quarantined output, and require successful write and readback before PASS. The recorded dry rehearsal used simulated paths and Ubuntu GnuPG (`docs/releases/v1-1/SUMMARY.md:104–111`). The real Tails clone and Tor fetch, device mount/eject, card discovery and PIN paths remain unverified by this offline review. The rehearsal's allowed Tor error records an incomplete source check. The online route list should include ORCID, which both sheets explicitly open (`docs/V1-RELEASE-PROCEDURE.md:127–129`).

**M7 — The install path can retrieve an unhashed build dependency.**
`service/verifier/install.sh:32–39`, `service/verifier/pyproject.toml:1–3`, `docs/releases/v1-1/SUMMARY.md:33–34`, `docs/V1-PROFILE.md:2013–2015`. The locked install of runtime dependencies uses hashes. The separate editable installation still enables build isolation and declares `setuptools>=68`. On a fresh machine that build step can resolve and execute a setuptools version outside the hashed lock. Pin and provision the build dependency under the hashed install path before the editable build, or use an installation path that requires no unlocked build dependency.

## LOW

**L1 — Reproducibility is conditional on ordinary Git object resolution and the same assembler.**
`service/verifier/release/release_tool.py:89–107,192–212`, `docs/releases/v1-1/SUMMARY.md:18–21`. The local in-memory build yielded 709203 bytes, 32 parts and the published SHA-256. Sorting the paths and manifest keys removes worktree order and environment timestamps from assembly. A repository with a local Git replacement ref can resolve the named commit to different tree content while a fresh clone resolves the original. Disable replacement refs in release reads. A genuine full comparison against an independently approved digest would stop on a divergent archive. The two documented builds use separate checkouts of the same assembler.

**L2 — The freeze hash trace is correct where given, but omits two catalog links and overstates pin scope.**
`docs/releases/v1-1/SUMMARY.md:44–61,69–77`, `docs/V1-RELEASE-PROCEDURE.md:155–159`, `formal/freeze-v1/FREEZE-RECORD.md:10–23`, `docs/V1-PROFILE.md:908–919`. Local Git blobs reproduce the stated archive, trust, constants, checker, signing script, freeze-record and catalog digests. The catalog's spec and vectors fields match the freeze table. The catalog also names the preamble and dependency manifest, whose freeze-table digests are absent from the trace. The public-key blob hash and the OpenTimestamps proof were outside this review's no-key/offline checks. Pin coverage is by supplied and required header heights across three proofs. A later-issued receipt whose required headers all fall within those same pinned ranges does not need new pins solely because of issue order. Conversely, a bundle for the first receipt can fail on an extra unpinned header or another verification condition. A proof whose required heights extend beyond the pinned ranges needs extended coverage. Also, the production sheet asks for ORCID comparison of the release fingerprint only, while the summary says the repository fingerprint is compared there too (`docs/ceremony/release-v1-1-SHEET.md:62–76`, `docs/releases/v1-1/SUMMARY.md:64–66`).
