# G1 logging confirmation — findings

Reviewed merged commit `6ca08e2` against the current checkout (`460a1de`). The classifications concern the findings in `CODEX-REVIEW.md`; the wider signer observations below are separate from the issuer logging contract. This is a source review, not evidence of deployed CloudWatch delivery. `pytest -q service/issuer/tests/test_logging.py` could not run because `pytest` is not installed on PATH.

## Original findings

1. **Poller notes disclose arbitrary exception text — PARTIAL.** Exception objects passed directly to `note` are rendered as class names in emitted notes (`service/issuer/tessera_issue/service.py:53-63`), including the reviewed poller handlers. But arbitrary strings are still emitted unchanged: `note("direct:", str(RuntimeError("https://host/?token=SECRET")))` emits the URL; the implementation does not enforce its fixed-tag claim. A production caller constructs `what` from verifier result strings before passing it to `note` (`service/issuer/tessera_issue/pipeline.py:1271-1272`), so its safety depends on those upstream values, not the logger. Separately, the API logs unvalidated event `httpMethod` and `resource` (`service/issuer/tessera_issue/lambda_app.py:73-74,84-85`): an event with a secret in `resource` emits it, even when the route is rejected. The normal API Gateway resource template is a deployment assumption, not a validation at this boundary.

2. **Synchronous logging can change deadline-sensitive execution — NOT FIXED.** `service/issuer/tessera_issue/logs.py:16-17` still synchronously writes stdout, without a timeout; removing flush does not bound write. A blocked write after a fence, SIGLOG insertion, or before an API response can still exhaust the invocation. This residual is now disclosed (`service/issuer/LOGGING.md:54-58`), not eliminated.

3. **Logging can replace an exception or abort processing — PARTIAL.** `emit`, API logging, and poll-summary wrappers now catch `BaseException` (`service/issuer/tessera_issue/logs.py:18-19`, `service/issuer/tessera_issue/lambda_app.py:76-77`, `service/issuer/tessera_issue/pipeline.py:180-184`), addressing the cited immediate stdout failure. However, `Issuer.note` first stringifies every argument and appends to its in-memory log outside the protection (`service/issuer/tessera_issue/service.py:53-55`). An adapter exception whose `__str__` raises, or an append raising `MemoryError`, can replace the original exception or abort the poll. A blocked write also remains a control-flow failure as above.

4. **Stage lines can omit committed changes and describe failed ones — PARTIAL.** Guarded poller saves now emit after success, and the tested failed-save and raise-after-commit cases are improved (`service/issuer/tessera_issue/pipeline.py:270-285`; `service/issuer/tests/test_logging.py:230-253`). Nevertheless `service/issuer/tessera_issue/api.py:98-103` commits `upload` → `frames` without a stage line; its API line does not contain the stage (`service/issuer/tessera_issue/lambda_app.py:73-75`). A process death or output failure after any successful save also leaves no transition line (`pipeline.py:273-278`). Conversely `api` and `poll_summary` are invocation records, not proof of a transition commit. A failed save itself does not emit a stage or guarded-transition line.

5. **Durable SIGLOG and CloudWatch line are not atomic — NOT FIXED.** `service/issuer/tessera_issue/pipeline.py:601-605` still writes SIGLOG before best-effort emission. Termination or stdout failure between them leaves an item without a line; a used-signature redelivery can skip the emission (`pipeline.py:578-591`). The documentation now accurately discloses the gap (`service/issuer/LOGGING.md:40-44`); this is not durable line coverage or a demonstrated alarm. The same post-commit gap applies to stage and lifecycle lines.

6. **Signer-controlled reason is bounded by syntax, not an allowlist — PARTIAL.** Unknown syntactically valid reasons now map to `UNRECOGNIZED_REASON` (`service/issuer/tessera_issue/pipeline.py:497-510`), so the cited `SECRET_CONTENT_123` is not emitted as a reason. The allowlist is incomplete: both signers forward verifier codec `Fault.code` (`service/signer-kms/tessera_sign_kms/signer.py:169-174`, `service/signer-gcp/tessera_signer/policy.py:109-114`), including `TAG_UNKNOWN` and `TAG_MISMATCH` (`service/verifier/tessera_verify/codec.py:162`; `service/signer-gcp/tests/test_policy.py:93-98`), neither in the set. For such a refusal, the issuer now stores `SIGNER_REFUSED:UNRECOGNIZED_REASON` and writes a diagnostic object instead of preserving the prior reason (`service/issuer/tessera_issue/pipeline.py:563-567`). Diagnostic storage adds a possible failure before SIGLOG/attempt completion; thus behavior beyond emitted logging changed. Mapping deliberately changes unknown reasons too, including for non-refusal statuses (`pipeline.py:523-530`); no claim of unchanged protocol behavior is justified.

7. **Coverage and metric-filter claims exceed the tests — PARTIAL.** New tests exercise direct exception objects, stdout exceptions, one known and one unknown refusal, malformed/bad signatures, and guarded saves (`service/issuer/tests/test_logging.py:132-179,194-253`). They do not establish the complete real-signer reason set, strings already constructed from exceptions, blocked output, the SIGLOG crash window, or deployed filters. For example, `TAG_UNKNOWN` from either real signer is not covered by the allowlist test, which checks only `SIGNING_STOPPED` (`test_logging.py:208-214`). The durable-coverage and synchronous-output limitations are now disclosed (`service/issuer/LOGGING.md:40-44,54-58`); no deployed alarm is established.

## Additional class findings

- **Signer output also exposes exception text and request-derived fields.** If the requested sweep includes signer service logs, the GCP signer logs `repr(exc)` on retries and response details (`service/signer-gcp/tessera_signer/signer.py:123-128,188-196`); its logger prints the fields (`service/signer-gcp/tessera_signer/main.py:83-84`). KMS logs exception-derived retry/refusal detail (`service/signer-kms/tessera_sign_kms/signer.py:244-264`) through `service/signer-kms/tessera_sign_kms/lambda_app.py:24-25`. For example, an SDK exception containing a pre-signed URL is emitted. These are distinct from the issuer's `LOGGING.md` promise.
- **Signer logging failures can change work.** The GCP signer logs a response after sending and deleting its queue message (`service/signer-gcp/tessera_signer/signer.py:192-198`); a logger exception prevents its normal return and reaches the handler-error path (`:214-219`). KMS logging occurs before a signed response is returned (`service/signer-kms/tessera_sign_kms/signer.py:263-268`); a failing logger can prevent that response. Both production loggers perform synchronous printing (`service/signer-gcp/tessera_signer/main.py:83-84`, `service/signer-kms/tessera_sign_kms/lambda_app.py:24-25`). These are outside the issuer fix but within the wider call sweep.
